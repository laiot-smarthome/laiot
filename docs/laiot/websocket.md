# WebSocket-сервер обновлений

Сервер нужен для того же сценария, что в alpha: значение свойства меняется
в фоне, а открытая страница показывает новое значение без перезагрузки.
Он не принимает команды и данные от браузера. Подписка на свойства
описывается короткоживущим тикетом, который выдаёт HTTP-эндпоинт после
проверки сессии администратора.

Кроме изменений свойств, сервер транслирует системные события
`system.*` и `module.<id>.*` в общий канал `system`. Их получает каждое
подключение панели.

## Что происходит по шагам

1. Blade-разметка помечает значения атрибутами `data-live-object` и
   `data-live-property` с системными именами. Это якоря: страница объявляет
   только те свойства, которые реально показаны, например `Light.status`.
2. `resources/js/laiot/websocket.js` собирает каналы «Объект.свойство» и
   отправляет их на `POST /api/v1/panel/websocket/ticket` с CSRF-заголовком.
3. Сервис проверяет сессию администратора, нормализует каналы, добавляет
   `system` и возвращает тикет, снимок текущих значений и курсор outbox.
4. Клиент применяет снимок и открывает `ws(s)://…/websocket`, передавая
   `laiot.v1` и тикет в `Sec-WebSocket-Protocol`. Тикет не попадает в URL и
   access-логи nginx.
5. `PropertyValueService` при изменении значения пишет строку в
   `websocket_events` в той же транзакции, что и значение. Наблюдатель
   `SystemEvents` пишет туда же системные события.
6. Процессы Workerman читают outbox, оставляют последнее событие на канал и
   отправляют массив изменений только тем подключениям, у которых этот
   канал есть. Системные события уходят всем подключениям в канал `system`.
7. При переподключении клиент снова получает снимок и курсор. Разрыв между
   снимком и сокетом закрывает реплей событий из тикета.

## Авторизация

Тикет — 64 шестнадцатеричных символа; в `websocket_tickets` хранится только
SHA-256. Он привязан к:

- id пользователя и отпечатку текущего хеша пароля (`stamp`);
- списку каналов и курсору снимка;
- сроку `WEBSOCKET_TICKET_TTL`, по умолчанию 300 секунд;
- признаку отзыва (`revoked_at`).

При подключении сервер повторно проверяет пользователя, роль администратора,
срок тикета и отпечаток пароля. По истечении тикета активное соединение
закрывается (код 4001), клиент получает свежий тикет и снимок и
переподключается — украденный тикет не даёт вечного доступа. Раз в
`auth_check` секунд активные подключения сверяются с таблицей: выход
из панели отзывает тикеты, а смена пароля или удаление пользователя
закрывают сокет. Сокет не принимает бизнес-сообщения: любой текстовый или
бинарный кадр закрывает соединение с кодом 1008.

Сессия и тикет — разные вещи. Сессия открывает панель, тикет разрешает
только чтение перечисленных свойств через WebSocket. API-токен для этого не
используется.

## Якоря на странице

Минимальный пример:

```blade
<div class="md-live-field"
     data-live-object="{{ $object['title'] }}"
     data-live-property="{{ $property['title'] }}">
    <x-md.input name="values[{{ $property['id'] }}]" :value="$values[$property['id']] ?? ''" />
</div>
```

Клиент обновляет вложенный `input`, `textarea` или `select`, пока поле не в
фокусе и пользователь его не менял. Если поле уже правится, обновление
пропускается; после потери фокуса догоняется последнее известное значение.
Для текстовых мест вместо формы используется дочерний элемент
`data-live-value`; можно также поставить `data-live-text` на сам якорь.
`data-live-map` задаёт JSON-карту отображения (`{"1":"Включено","0":"Выключено"}`).

Сейчас якоря размещены на вкладке «Свойства и значения» карточки объекта.
Новые страницы подключаются теми же двумя атрибутами, без отдельного
эндпоинта и без подписки на весь класс или дом.

## Протокол

Сервер отправляет JSON-объекты с `v: 1`.

```json
{"v":1,"type":"ready","user":{"id":1,"name":"Администратор"},"channels":3,"system":true,"cursor":42,"server_time":"2026-10-29T14:00:00+03:00"}
```

```json
{"v":1,"type":"changes","events":[[43,"Light.status","1","2026-10-29 14:00:01"]]}
```

Элемент `events` — массив `[id, "Объект.свойство", value, created_at]`.
Клиент хранит последний id по каждому каналу, поэтому пакеты можно безопасно
повторять; устаревшие и дублирующиеся события игнорируются. Ошибка
авторизации приходит как `{"v":1,"type":"error","code":"unauthorized"}` с
кодом закрытия 4401.

Системное событие приходит отдельным сообщением:

```json
{"v":1,"type":"system","id":44,"event":"system.minute","data":{"occurred_at":"2026-10-29T15:00:00+03:00"},"at":"2026-10-29 15:00:00"}
```

Страница слушает его обычным событием:

```js
window.addEventListener('md:websocket:system', (event) => {
    console.log(event.detail.event, event.detail.data);
});
```

Системные события не привязаны к конкретному полю и не заменяют
`property.changed`, сценарии или уведомления. Это тот же поток
`system.*`/`module.<id>.*`, который уже получают модули, отправленный
открытой панели.

## Устойчивость и объём

- Outbox `websocket_events` — долговечная граница между записью значения и
  доставкой. Значение и событие коммитятся одной транзакцией; сбой сервера
  не теряет уже сохранённое значение.
- За один проход процесс читает до `batch` строк и отправляет одно событие
  на канал. Частые изменения не раздувают трафик: странице нужно последнее
  значение.
- Реплей после снимка ограничен `replay_limit`; снимок уже содержит
  актуальное состояние, поэтому ограничение не оставляет «дыр» в обычном
  сценарии.
- Медленный клиент закрывается по переполнению буфера отправки (1013), а не
  копится в памяти процесса.
- Ограничение `max_connections` действует на процесс; общий предел —
  значение, умноженное на `workers`.
- Сервер переподключается с экспоненциальной паузой; после восьми неудач
  ждёт следующего открытия вкладки или события `online`.
- Старые строки outbox чистит сам сервер по `retention_hours`; тикеты —
  через семь дней после истечения.

Каждый процесс читает общий outbox и обслуживает свои подключения. Это
простая и предсказуемая схема для домашней установки и нескольких
процессов. Межпроцессного брокера, отдельного потока рассылки и
распределённой блокировки здесь нет; при росте числа процессов стоит
измерить нагрузку на БД и при необходимости вынести чтение outbox в один
процесс.

## Настройки

Параметры хранятся в `.env` и редактируются в разделе «WebSocket»
страницы `/settings`. После изменения перезапустите процесс `websocket`.

| Ключ | По умолчанию | Назначение |
| --- | --- | --- |
| `WEBSOCKET_ENABLED` | включено | Выдача тикетов и запуск сервера |
| `WEBSOCKET_HOST` | `127.0.0.1` | Интерфейс прослушивания |
| `WEBSOCKET_PORT` | `8081` | Порт Workerman |
| `WEBSOCKET_PATH` | `/websocket` | Путь рукопожатия |
| `WEBSOCKET_PUBLIC_URL` | пусто | Публичный `ws://`/`wss://` адрес; пусто — хост панели |
| `WEBSOCKET_WORKERS` | `2` | Процессов на Linux |
| `WEBSOCKET_TICKET_TTL` | `300` | Срок тикета, секунды |
| `WEBSOCKET_MAX_CONNECTIONS` | `1000` | Подключений на процесс |
| `WEBSOCKET_ROOT_DOMAIN` | пусто | Корневой домен: разрешены он и все поддомены |
| `WEBSOCKET_ALLOWED_ORIGINS` | пусто | Точные Origin через запятую; заменяют правило домена |

Остальные значения — `poll_ms`, `batch`, `replay_limit`,
`max_channels`, `heartbeat`, `auth_check`, `prune_interval` и
`retention_hours` — заданы в `config/websocket.php` и не выводятся в общую
форму, чтобы не превращать её в панель тюнинга.

По умолчанию Origin разрешается для корневого домена и всех его поддоменов.
Корень берётся из `WEBSOCKET_ROOT_DOMAIN`, иначе из хоста
`WEBSOCKET_PUBLIC_URL`, `BASE_URL` или `Host` самого подключения. Если нужен
закрытый список конкретных origin'ов, заполните `WEBSOCKET_ALLOWED_ORIGINS`:
он заменяет правило домена, а не дополняет его. Схема допустима только
`http` или `https`; порт при сравнении домена не учитывается.

## Запуск

Миграции добавляют `websocket_events` и `websocket_tickets`:

```bash
php bin/laiot db:migrate
```

Foreground-процесс для systemd:

```bash
php bin/laiot websocket start
```

Управление на Linux:

```bash
php bin/laiot websocket status
php bin/laiot websocket restart
php bin/laiot websocket stop
```

Шаблон unit — `deploy/systemd/laiot-websocket.service`. Он рассчитан на
раскладку releases (`@@ROOT@@/current`) и подставляет пользователя, группу
и корень так же, как остальные шаблоны `deploy/systemd`. При прямой
раскладке замените `WorkingDirectory` и `ExecStart` на `@@ROOT@@` и
`@@ROOT@@/bin/laiot`, а `ReadWritePaths` — на `@@ROOT@@/var`.

Nginx должен проксировать WebSocket на локальный порт; наружу `WEBSOCKET_PORT`
обычно не публикуется:

```nginx
location /websocket {
    proxy_pass http://127.0.0.1:8081;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header Origin $http_origin;
    proxy_read_timeout 3600s;
}
```

`WEBSOCKET_PUBLIC_URL` нужен, если браузер ходит на другой хост или порт,
чем панель. Для того же хоста через nginx оставьте пусто.

## Ограничения

- Каналы не проверяют отдельное право на свойство: панель уже требует
  администратора, а список каналов — фильтр, а не мандат. При появлении
  гранулярного доступа к объектам проверку нужно добавить в выдачу тикета.
- Снимок читает `property_values`; значения, записанные в обход
  `PropertyValueService`, не порождают событие WebSocket.
- Тикет в `Sec-WebSocket-Protocol` поддерживают браузеры и обычные прокси;
  клиент, который не умеет этот заголовок, должен использовать тот же
  протокол вручную.
- Windows подходит для разработки и одного процесса; fork, pid-файл,
  `stop/status` и systemd проверяются в Linux.
- Это не замена очереди событий и не транспорт для входящих команд
  устройствам. Для команд остаются MQTT-модуль и очередь.
