# HTTP API LaIOT

Источник контракта — `routes/api.php` и соответствующий контроллер.
Это API нового ядра, а не обещание полной совместимости с API alpha.
API v2 и единый OpenAPI-контракт пока не реализованы.

## Маршруты и доступ

| Метод и URL | Доступ | Назначение |
| --- | --- | --- |
| `GET /api/v1/health` | Публичный | Готовность БД и прикладного кэша |
| `GET /api/v1/about` | Публичный | Версия сборки, PHP, счётчик модулей |
| `GET /api/v1/modules` | Публичный | Список подключённых SDK-модулей |
| `GET /api/v1/me` | Bearer или X-API-Key | ID владельца токена, роли и разрешения |
| `GET /api/v1/panel/search` | Браузерная сессия | Поиск по ядровым сущностям |
| `GET /api/v1/panel/notifications` | Браузерная сессия | Непрочитанные уведомления и сводка |
| `POST /api/v1/panel/notifications/dismiss` | Сессия + CSRF | Прочитать одно или группу уведомлений |
| `GET /api/v1/panel/attention` | Браузерная сессия | Бейджи меню: ошибки за сутки, сбойные задания, непрочитанные |
| `GET /api/v1/panel/linked-object` | Браузерная сессия | Поиск объекта и его свойства/методы |
| `GET/POST/PUT/PATCH/DELETE /api/v1/webhooks/{secret}` | Секрет в пути | Входящий webhook |

Полный список текущего kernel можно посмотреть `route:list --json`.
Не подставляйте токен в query string. Для JSON-ошибок явно передавайте
`Accept: application/json`; один префикс `/api/v1` не заставляет все
ошибки kernel сериализоваться в JSON.

## Форматы ответов различаются

Успешный `/me` возвращает поля напрямую:

```json
{"user_id": 7, "roles": ["admin"], "permissions": ["*"]}
```

Панельные контроллеры поиска и уведомлений используют обёртку:

```json
{"ok": true, "data": {"total": 0, "items": []}}
```

Поля внутри `data` зависят от endpoint; пример выше не является схемой
поиска. Поиск отдаёт `sections`, `counts`, `total`; уведомления — `items`,
`total`, `counts`, `levels`, `severity`, `offset`.

Общие ошибки `ErrorResponse` имеют вид:

```json
{"ok": false, "error": {"code": "not_found", "message": "Not Found"}, "request_id": "example"}
```

Сессионные auth/CSRF-ошибки и webhook возвращают собственные JSON-ответы
без обязательного `request_id` в теле. У ответов, прошедших kernel,
присутствует заголовок `X-Request-Id`. Единого конверта `{ok,data,meta}`
сейчас нет; клиент не должен безусловно разворачивать `data` у каждого URL.

## Health и HTTP-ошибки

Health отдаёт 200 при доступных БД и кэше, иначе 503. Поля:
`status=ok|degraded`, `app`, `database=ok|not_configured|unavailable`,
`cache=ok|failed|unavailable`. Проверка кэша записывает и удаляет короткий
диагностический ключ. Это не проверка worker, Mosquitto или systemd-агента.

400 `bad_request` — некорректная структура входных полей, например массив
вместо строки поиска; 404 — маршрут не найден; 405 — метод не подходит,
с заголовком `Allow`;
401 — требуется аутентификация; 403 — право/CSRF/выключенный вход;
429 — лимит входа; 500 — ошибка сервера. В режиме обслуживания kernel
возвращает 503 и `Retry-After: 60` для закрытых маршрутов, включая webhook.
Браузерный запрос без `Accept: application/json` на 404/405/500/503 получает
HTML-страницу панели с маскотом, request id и действиями; JSON-клиент —
конверт `ErrorResponse` выше. В debug необработанное исключение показывает
браузеру страницу с исходником и стеком; JSON-контракт сохраняется, поле
`error.debug` содержит только сообщение. Ранние ошибки Composer/boot тоже
получают 500, а подробности доступны только после загрузки Config.

## Панельные запросы

- Поиск: `?q=<текст>&limit=<число>`; ограничения нормализуются сервисом
  `PanelSearch`. Очень короткий запрос не запускает полноценный поиск.
- Linked object: `?q=` для поиска; `?object=` для выбранного объекта и
  контекста его класса.
- Уведомления: `?module=&offset=`; прочтение — тело с `id` либо `module`,
  плюс CSRF-заголовок. Детальный контракт —
  [notifications.md](notifications.md).
- Внимание: ответ `{badges: {system_errors, jobs, notifications}}`, у каждого
  `count`, `tone`, `title`; счётчики ничего не меняют и нужны только бейджам
  бокового меню.

API-токен не заменяет сессию на этих маршрутах. Внешний клиент должен
использовать именно предусмотренный для него способ доступа.

## Входящие webhook

Управление находится в ядровом разделе `/api`, реализация —
`app/Http/Controllers/WebhookController.php` и `app/Services/Webhooks`. Данные лежат в `api_webhooks`, без ModuleDb.
Секрет — 48 шестнадцатеричных символов; в таблице хранится его SHA-256.
Открытый секрет показывается только при создании/ротации. После ротации
старый URL перестаёт совпадать с записью.

Endpoint принимает пять HTTP-методов, затем сервис проверяет allowlist
конкретного входа. Неизвестный секрет — 404, запрещённый метод — 405 с
`Allow`, выключенный вход — 403. Код/сценарий выполняется синхронно,
публичный ответ не раскрывает текст исключения обработчика.

В `$params` обработчика доступны `payload`, `method`, `headers`, `webhook`.
JSON-массив/объект становится payload; прочее непустое тело — `['raw' => ...]`;
без тела используются поля формы. Query string не сливается с payload.
Успех оборачивается в `{"ok":true,"data":...}`; ошибки — в `ok=false/error`.
В записи обновляются только последние время и статус, не полный журнал
всех вызовов. Код webhook доверенный, не PHP-песочница.

## Граница со старым входом

Legacy `public/api.php` удалён вместе с alpha-runtime. Точный `/api` — новая
браузерная страница, `/api/v1/*` — новое API, остальные маршруты идут через
`public/index.php`. Внешняя маршрутизация CRUD webhook в nginx пока не
настроена: нового стенда нет, проверка идёт прямым вызовом Application.

Сейчас `routes/web.php` содержит также `/api/create` и `/api/{id}/...`,
но правила nginx/dev server отдают общий `/api/*` legacy-входу. Поэтому
редактирование webhook через реальные URL требует согласования этих
правил; прямой тест kernel не доказывает работу через nginx. Подробность
зафиксирована в [limitations.md](limitations.md); документация её не маскирует
несуществующим исправлением маршрутизации.
