# Шифрование секретов

`illuminate/encryption` 12 подключён через `EncryptionServiceProvider`.
Для токенов и паролей внешних интеграций, которые нужно впоследствии
прочитать, используется общий шифратор AES-256-CBC. Собственные алгоритмы,
форматы зашифрованных данных и случайный ключ при каждом запуске не нужны.
Пароли пользователей хешируются; обратимое шифрование для них не применяется.

## Ключ приложения

При установке через `/install` или `php bin/laiot install` установщик
автоматически создаёт криптографически случайный ключ из 32 байт и сохраняет
`APP_KEY="base64:..."` в `.env`. Пользователь не вводит ключ и не видит его
в результате установки. Ключ установщика `var/install.key` — другой секрет.

Существующий корректный APP_KEY сохраняется, в том числе после сбоя и
повторной установки. Значение окружения процесса имеет приоритет; если оно
задано, новый ключ не генерируется. Некорректный ключ вызывает явную ошибку,
его значение не включается в сообщение.

Ключи входят в `SettingsSchema::environmentFields()`, но не в редактируемые
поля панели. Настройки приложения — `encryption.key` и
`encryption.previous_keys` в `config/encryption.php`. `APP_PREVIOUS_KEYS`
принимает старые ключи через запятую: новые данные шифруются текущим ключом,
старые могут расшифровываться предыдущими. Автоматического перешифрования
существующих записей нет.

Храните резервную копию ключа отдельно от данных. Потерянный ключ не
восстанавливается из БД. Ключ нельзя выводить в HTML, журнал, сериализованную
конфигурацию или ответ API. После изменения ключей фоновые процессы нужно
перезапустить. Для установок, созданных до подключения шифрования, APP_KEY
нужно подготовить до первой записи зашифрованных полей; обычный boot его
не создаёт и `.env` не меняет.

## Сервисы и модели

Через DI доступны `Illuminate\Encryption\Encrypter`, контракты
`Illuminate\Contracts\Encryption\Encrypter` и `StringEncrypter`, а также
имя `encrypter`. Это один ленивый экземпляр на Application. Пример для
сервиса с зависимостью `StringEncrypter $encryption`:

```php
$stored = $encryption->encryptString($token);
$token = $encryption->decryptString($stored);
```

Модели от `LaIOT\Models\Model` используют штатные casts Eloquent:

```php
protected $casts = [
    'access_token' => 'encrypted',
    'credentials' => 'encrypted:array',
];

protected $hidden = ['access_token', 'credentials'];
```

Также доступны строковые casts `encrypted:json`, `encrypted:object` и
`encrypted:collection`. Шифратор берётся из текущего контейнера, без
Laravel-фасада Crypt и общего ключа для разных экземпляров Application.
Классы casts, напрямую использующие фасад Crypt, например
`AsEncryptedArrayObject`, этой интеграцией не подключены.

В БД хранится шифротекст, при обращении к атрибуту — расшифрованное значение.
`null` остаётся `null`. Поле должно иметь достаточную длину, обычно TEXT:
шифротекст длиннее исходного значения. По зашифрованному значению нельзя
выполнять обычный поиск или проверку уникальности.

Шифрование не скрывает расшифрованный атрибут при `toArray()`/JSON:
секретные поля обязательно добавляйте в `$hidden`, в ответы передавайте
только разрешённые поля. Query Builder, включая ModuleDb, не применяет
casts модели: там используйте общий шифратор явно. Повреждённые данные или
неподходящий ключ должны давать ошибку; возврат исходного текста вместо
расшифровки запрещён. Переход существующей plaintext-колонки на encrypted
требует отдельного переноса данных, простая смена cast их не преобразует.

## Проверки

`EncryptionTest` проверяет шифротекст в SQLite, чтение casts, null, скрытые
поля, повреждение данных и предыдущие ключи. `InstallServiceTest` проверяет
создание APP_KEY и его сохранение после сбоя. Все ключи тестовые;
рабочий `.env` не подключается.
