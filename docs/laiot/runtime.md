# Фоновый runtime

В приложении три разных вида фоновой работы: задачи SDK-модуля, очередь
именованных заданий и пользовательские таймеры. Они не запускаются из
HTTP автоматически. Linux/systemd — рабочая платформа; Windows подходит
для доступных тестов, но не доказывает корректность fork и Unix-сокетов.

## Worker SDK-модуля

Манифест объявляет tasks, entrypoint предоставляет публичный метод:

```json
{
  "tasks": {
    "poll": {"method": "poll", "interval": 60, "timeout": 30, "enabled": true}
  }
}
```

```php
public function poll(\LaIOT\Services\Worker\BackgroundTaskContext $context): void
{
    // Один проход. Планирование и повторный вызов принадлежат worker.
}
```

Команды: `worker <id>` — постоянный процесс; `worker <id> --once` —
один проход включённых задач. Нужен подключённый модуль с entrypoint и
вызываемым методом. Модуль без включённых tasks заканчивает работу без
создания полезной фоновой нагрузки.

Один worker обслуживает задачи модуля последовательно. Манифест разрешает
interval 1–86400 секунд и timeout 1–3600 секунд, значения по умолчанию 60.
По сигналам SIGTERM/SIGINT выставляется флаг остановки; ошибка задачи
пишется в журнал и состояние, а не обязательно завершает весь worker
ошибочным кодом. Проход --once не является sandbox или симуляцией.

При доступных pcntl_fork/pcntl_waitpid задача выполняется в дочернем
процессе. Родитель ждёт, контролирует deadline и завершает просроченного
ребёнка через posix_kill. Нужны проверенные pcntl/posix в Linux.
Без pcntl код исполняется в текущем процессе без принудительного timeout.
SIGTERM/SIGINT, полученный родителем, пересылается дочерней задаче: в
контейнере сигнал приходит только PID 1, и без пересылки длинный цикл
интеграции остался бы сиротой с блокировками. Если после жёсткого kill в
CacheStore остался `worker.lock.<id>` с TTL 120 секунд, а файловая
ProcessLock уже взята, worker перехватывает кэш-ключ — ждать TTL и
простаивать две минуты после рестарта не нужно.

### Долгоживущая интеграция

Большинству задач нужен один короткий проход, но интеграции с соединением
(сейчас MQTT) держат цикл до своего `timeout` — это разрешённый длинный
обработчик, а не второй планировщик. `BackgroundTaskContext::once` сообщает,
что запущен разовый `--once`: такой проход должен завершиться быстро (MQTT
ограничивает его двумя секундами), иначе команда диагностики повиснет на
час. Перед fork worker закрывает PDO родителя, кроме SQLite в памяти: иначе
два процесса используют один TCP-сокет и следующий запрос получает чужие
ответы. MQTT дополнительно проверяет соединение в дочернем процессе, если
оно всё же было открыто. Устройство цикла — [mqtt.md](mqtt.md).
Состояние PHP-объекта, изменённое ребёнком, не переносится назад в память
родителя: долговечные результаты сохраняйте через сервисы/хранилище.

## Состояние и lock

BackgroundTaskState использует общий CacheStore:

| Данные | Логическое имя ключа | TTL |
| --- | --- | --- |
| Lock модуля | `worker.lock.<id>` | 120 секунд |
| Lock ядровой задачи | `worker.lock.core.<task>` | 120 секунд |
| Состояние задачи | `worker.task.<id>.<task>` | 86400 секунд |

Физические ключи также имеют префикс CacheStore, обычно `laiot.`.
Состояние содержит сведения о запуске/завершении, ошибке и следующем
выполнении; это не бесконечный журнал всех запусков.

Для production предполагается Redis. Конструктор не запрещает file/array,
поэтому правильный драйвер должен быть настроен явно. Array не разделяет
lock между процессами. Дополнительно worker удерживает файловую блокировку
в `var/locks` на всё время работы, включая длительный обработчик; общий
worker событий блокирует все свои полосы. Файлы блокировок нельзя удалять,
пока работают процессы. Все worker одной установки должны использовать
один каталог на локальной файловой системе. Это не распределённая блокировка
между разными серверами или независимыми каталогами releases.

TTL ключа Redis по-прежнему составляет 120 секунд; очистка прикладного кэша
удаляет эти ключи, но не файловые блокировки. Команды `queue:work` работают
вне блокировок постоянных worker и не должны параллельно обслуживать полосу
событий, где требуется последовательная обработка.

Планирование внутри worker использует также локальное состояние процесса;
наличие next_run в Redis не означает полностью распределённый планировщик
с восстановлением всех интервалов после любого рестарта.

## Процессы ядра

`core-worker queue` постоянно обслуживает очередь default;
`core-worker events` — очередь событий свойства (OnChange, история, постановка
доставки модулям); `core-worker timeouts` — созревшие записи runtime_timeouts;
`core-worker maintenance` — retention истории, журнала, заданий, таймеров и
ошибок.
`core-worker module.<id>` обслуживает привязки и события одного модуля отдельно
от его задач (`laiot-core@module.<id>`). `worker <id>` выполняет задачи; без
отдельного процесса доставки он также обслуживает очередь `module.<id>`.
Для малой задержки команд используйте отдельный процесс доставки и Linux с
`pcntl`/`posix`: обработчик ограничен `queue.handler_timeout`, по умолчанию
5 секунд. Ожидание пустой очереди ядра — 100 мс. `--once` ограничивает их одним
шагом/проходом. Разовые `queue:work` и `timeout:run` не заменяют постоянный
сервис. Семантика повторов — [queue.md](queue.md).

Шаблоны: `deploy/systemd/laiot-worker@.service` и
`deploy/systemd/laiot-core@.service`. MemoryMax=256M ограничивает сервис;
ядровой шаблон добавляет Nice=-5 и CPUWeight=500. Это задаёт приоритет,
но не гарантирует задержку jobs при общей занятости БД, диска или CPU.
Сами PHP-классы не устанавливают такой предел памяти вместо systemd.

`core-worker events` запускается как `laiot-core@events` и обслуживает все
полосы очереди по кругу. Для параллельной работы запускается по процессу на
полосу: `laiot-core@events.0`…`laiot-core@events.<N-1>`, где N —
`queue.events_lanes`. Одна полоса всегда обслуживается одним процессом: так
сохраняется порядок изменений одного свойства. Без запущенного events
значения сохраняются, но история, журнал и OnChange отстают, поэтому сервис
обязателен.

`laiot-core@maintenance` запускается одним процессом на установку и делает
очистку по срокам из `config/retention.php`: сразу при старте и далее раз в
`retention.interval` секунд. Ошибка очистки попадает в канал `queue` и не
останавливает сервис. Ручной прогон — `db:prune [--dry-run]`; подробности —
[logging.md](logging.md).

## WebSocket

`php bin/laiot core-worker websocket` — штатная ядровая служба
`laiot-core@websocket`. Внутри неё Workerman обслуживает исходящие обновления свойств и системные
события, входящие сообщения не принимает. Подписку на каналы выдаёт
HTTP-эндпоинт после проверки сессии; события читаются из outbox
`websocket_events`.
Процесс не запускается из HTTP и не заменяет очередь событий. Настройки,
протокол, nginx и шаблон unit — [websocket.md](websocket.md). Как и остальные
фоновые службы, он требует Linux для fork и systemd; Windows подходит для
одного процесса и локальной проверки.

## Supervisor циклов

`core-worker supervisor` — постоянный контроль каждые пять секунд.
При старте он через Unix-агент запускает обязательные core-службы,
worker включённых модулей и отдельные процессы доставки `module.<id>`.
Изменение включённых модулей перечитывается без повторного boot обработчиков.
Выключенный WebSocket не запускается. Штатный профиль использует один
`events`, обслуживающий все полосы; отдельные `events.<n>` одновременно
не запускаются и в таблице X-Ray не изображаются упавшими процессами.

Systemd автоматически перезапускает аварийно завершённые процессы.
Supervisor следит за `NRestarts`, состоянием службы и heartbeat:
падение/неожиданная остановка пишется в `/errors`, а отсутствие heartbeat
более 150 секунд дополнительно вызывает перезапуск. Повторяющаяся ошибка
контроля подавляется на пять минут. Ошибки задач модулей также попадают
в журнал ошибок; одинаковые последовательные ошибки одной задачи не
дублируются до успешного прохода. Родитель worker продолжает обновлять
heartbeat, пока ждёт длинную дочернюю задачу.

Явная остановка из X-Ray сохраняется до следующего старта supervisor.
Она показывается предупреждением, а не неожиданным падением. После
перезапуска системы включённые процессы снова поднимаются автоматически.
Сам supervisor также обслуживается systemd с автоматическим рестартом.

## Административный агент

`bin/laiot-agent` — отдельный процесс, в шаблоне сервиса работает от root.
Веб-приложение не должно само писать `/etc/systemd/system` или выполнять
произвольный systemctl. Связь — JSON через Unix socket, по умолчанию
`/run/laiot/agent.sock` с правами 0660.

Настройки берутся из `/etc/laiot/agent.json`, а не из рабочего `.env`.
`LAIOT_AGENT_CONFIG` меняет путь к JSON. Пример структуры с условными
значениями, которые администратор заменяет для своей установки:

```json
{
  "root": "/srv/laiot",
  "user": "laiot",
  "group": "laiot",
  "socket": "/run/laiot/agent.sock",
  "systemctl": "/usr/bin/systemctl",
  "unit_dir": "/etc/systemd/system",
  "allowed_uid": 1000
}
```

Действия протокола:

- `worker.start/stop/restart/status`, поле module с ID модуля.
- `core.start/stop/restart/status`, поле module: queue либо timeouts.
- `workers.sync`, поле modules со списком желаемых модулей.
- `cores.sync`, поле tasks со списком ядровых задач.
- `worker.install` — установка обоих шаблонов через installAllUnits.

```json
{"action": "worker.restart", "module": "weather"}
```

Ответ: `ok` и `data` либо `ok=false/error`. Имена проверяются контроллером,
аргументы systemctl передаются массивом без shell-конкатенации. Доступ к
сокету является административной возможностью и должен быть ограничен
владельцем/группой. allowed_uid проверяется только при наличии
posix_getpeereid; нельзя обещать обязательную проверку peer UID на каждой
Linux-сборке PHP.

## Установка: что существует сейчас

Приложение ставится страницей `/install` или командой
`php bin/laiot install`: проверки PHP, расширений, прав, БД и Redis,
запись `.env`, миграции и первый администратор. Страница работает до
появления базы и закрыта одноразовым ключом `var/install.key`; после
успеха появляется `var/installed.lock`, а `/install` отвечает 404.
Подробности — [install.md](install.md).

Системная часть — отдельная операция: пользователь и права, каталоги,
systemd-юниты и агент. Для Ubuntu это делает `deploy/setup-ubuntu.sh`,
описание и ограничения — [deploy.md](deploy.md). Запуск служб не является
побочным эффектом открытия панели.

Сервис агента описан в `deploy/systemd/laiot-agent.service`; пути и
пользователи в шаблонах подставляются из конфигурации SystemdController.
`php bin/laiot-agent install` по-прежнему устанавливает только
worker-шаблон: оба шаблона ставит `installAllUnits` и действие протокола
`worker.install`, а скрипт окружения делает это за администратора.

Проверять владельца сокета, пользователя worker, абсолютный root,
зависимости PHP, Redis и фактическую работу юнитов нужно на Linux.
Docker-стенд без systemd не заменяет эту проверку.

## Обновление остаётся проектом

Принятое направление: пользователь запускает обновление вручную,
доступность версии проверяется отдельно, сборка — на его сервере,
переключение releases/current атомарное, после health — подтверждение или
откат. Установка Composer/npm, миграции и рестарт должны иметь обработку
ошибок и проверенный порядок.

UpdateService, кнопка обновления, автоматизированный откат и supervisor-
адаптер пока не реализованы этим runtime. Старый deploy alpha не является
эквивалентом нового update-процесса. Будущие шаги — в мастер-плане;
не выдавайте их за уже доступные команды.

## Системные события времени

`php bin/laiot core-worker system-events` запускает отдельный генератор.
При переходе минуты он создаёт `system.minute`, при начале часа также
`system.hour`, при начале дня также `system.day`. Границы определяются
часовым поясом приложения (`config/app.php`). В `occurred_at` передаётся
начало минуты в ISO 8601 с часовым смещением.

При запуске текущая минута принимается за исходную: прошлые события не
восстанавливаются. При скачке времени промежуточные минуты не генерируются.
`--once` только выполняет один проход и не генерирует событие при старте.
Запускайте один процесс на установку; блокировка предотвращает второй запуск.
Для systemd используется существующий шаблон `laiot-core@system-events`.

Подписка модуля и доставка описаны в [SDK](sdk.md). Если процесс генератора
или worker модуля не запущен, генерация или обработка соответственно не
происходит. Уже поставленные задания остаются в очереди модуля и выполняются
после его запуска согласно правилам очереди.

Сценарий тоже может быть привязан к событию ядра или модуля: поле
`scripts.event_name` на странице `/scripts` (пусто — только ручной запуск).
Имя события показывает владельца: `system.*` отправляет ядро,
`module.<id>.*` — модуль. Наблюдатель ядра ставит на каждое подходящее
событие задание `script.system.event` в очередь `default`, а выполняет его
`core-worker queue`, а не процесс генератора. Поэтому медленный сценарий не
задерживает `system.minute`, а ошибка одного сценария не останавливает
остальные: исключение пишется в лог приложения, задание не переводится в
failed и следующее событие снова запускает сценарий. В `$params` сценарий
получает `event` и `data` (`occurred_at` для событий времени).

У сценария есть режим без ядра: в форме снят флажок «Подключать ядро». Тогда
код выполняется отдельным процессом `php` как обычный файл — без bootstrap,
без `gg/sg/callMethod` и других функций ядра; доступны только чистый PHP и
`$params`. Это не sandbox: код работает под тем же пользователем и с теми же
правами на файлы. Отдельный процесс имеет тайм-аут 10 секунд, поэтому
зависший сценарий не держит очередь и панель бесконечно. Запуск из формы
(кнопка «Выполнить») и запуск по событию используют один и тот же выбор.

Важно про параллельность. Кнопка «Выполнить» — это HTTP-запрос: разные
запросы выполняются параллельно на свободных процессах PHP, а блокировка
сессии отпускается перед запуском кода. А вот задания из очереди выполняет
один `core-worker queue`, поэтому запуски сценариев по событиям идут строго
последовательно, даже если коды независимы. Тайм-аут 10 секунд относится
только к режиму без ядра: сценарий с ядром тайм-аута не имеет и может
задержать очередь. Отдельных полос или параллельных процессов для сценариев
пока нет — это следующий шаг, если понадобится.

Веб-слой — nginx + PHP-FPM; Apache и mod_php в проекте нет. Пул FPM задаётся
в `pool.d` на хосте или в контейнере `app`; приложение намеренно не читает
`pm.max_children` и `request_terminate_timeout`, чтобы вывести из них лимит
запусков. Пул живёт вне приложения, может быть общим и динамическим, а
`max_children` — статический потолок, а не число свободных процессов; другие
запросы панели и соседние сайты занимают те же воркеры.

Практическое правило: `pm.max_children` должно покрывать панель и
одновременные запуски сценариев с запасом. Если нужно ограничить именно
ручные запуски, это будет собственный параметр (`scripts.max_concurrent` с
семафором в кэше), значение которого владелец подбирает под свой пул вручную;
число полос для событийных запусков — тоже наш конфиг, а не FPM. Внешний
потолок одного HTTP-запроса с ядром — `request_terminate_timeout` в пуле; у
очереди такого внешнего тайм-аута нет.
