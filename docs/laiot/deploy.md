# Установка системной части

`deploy/setup-ubuntu.sh` — скрипт первичной настройки Ubuntu для LaIOT. Он
делает только системную часть, которую нельзя безопасно выполнить из
веб-приложения: проверяет окружение, создаёт каталоги `var`, выставляет
владельца и права, устанавливает systemd-юниты и настраивает
административный агент.

Полный сценарий для чистой Ubuntu — [SSH-мастер сервера](server-installer.md):
он ставит FastPanel, PHP, Redis, сайт и зависимости. Этот скрипт нужен,
когда код уже развёрнут, а systemd-слой требуется установить или починить
повторно; он идемпотентен и умеет `--dry-run`.

Скрипт не является установщиком приложения. Данные установки — `.env`,
миграции и администратор — записывает `/install` или CLI `install`
([console.md](console.md)). Поэтому скрипт не читает и не меняет `.env`, не
подключается к базе и не трогает файлы приложения. Повторный запуск скрипта
безопасен: он проверяет текущее состояние и меняет только недостающее.

## Граница с /install

| Что | `/install` и `install` | `setup-ubuntu.sh` |
| --- | --- | --- |
| `.env`, доступ к БД и Redis | да | нет |
| Миграции и администратор | да | нет |
| Системный пользователь | нет | проверяет, что существует |
| Каталоги `var` и права | только использует | создаёт и выставляет |
| systemd-юниты | нет | рендерит и устанавливает |
| Агент и сокет | проверяет доступность | настраивает конфиг и службу |
| nginx, PHP-FPM, MariaDB, Redis | нет | нет, остаются вручную |

Рекомендуемый порядок: развернуть код и зависимости, запустить скрипт,
открыть `/install`. Обратный порядок не запрещён, но до `/install` ядровым
службам нечего обслуживать: без `.env` они не подключатся к базе и будут
перезапускаться. Поэтому по умолчанию скрипт только включает автозапуск, а
не стартует ядровые процессы.

## Требования

- Ubuntu с systemd как init. В контейнере без `/run/systemd/system` скрипт
  остановится: запускать юниты там нечему.
- Запуск от root: меняются systemd, владельцы и права файлов.
- Код приложения уже развёрнут: есть `bin/laiot`, `bin/laiot-agent`,
  каталог `deploy/systemd` и `vendor/autoload.php` после `composer install`.
- PHP 8.2 или новее в `PATH` с расширениями `pdo_mysql`, `mbstring`,
  `intl`, `curl`, `openssl`, `pcntl`, `posix`. Шаблоны вызывают
  `/usr/bin/php`, поэтому этот путь тоже должен существовать.
- Пользователь и группа уже созданы. Скрипт не вызывает `useradd`:
  создание системной учётной записи — отдельное осознанное действие
  администратора. Он проверяет наличие и завершается с подсказкой.
- Пути не содержат пробелов, символа `%`, кавычек и обратных косых черт:
  шаблоны systemd не экранируют их, а `%` система трактует как спецификатор.
- nginx, PHP-FPM, MariaDB и Redis установлены и настроены отдельно. Скрипт
  их не устанавливает и не правит их конфигурацию.

## Запуск

Сделайте файл исполняемым и сначала посмотрите план:

```bash
chmod +x deploy/setup-ubuntu.sh
sudo deploy/setup-ubuntu.sh --dry-run
```

Обычный запуск с параметрами по умолчанию:

```bash
sudo deploy/setup-ubuntu.sh
```

Другой каталог, пользователь и сразу запуск ядровых служб:

```bash
sudo deploy/setup-ubuntu.sh --root /srv/laiot --user laiot --start
```

Перезапись ранее установленных юнитов и `agent.json`:

```bash
sudo deploy/setup-ubuntu.sh --force
```

| Опция | По умолчанию | Назначение |
| --- | --- | --- |
| `--root PATH` | `/var/www/laiot` | каталог установки |
| `--user NAME` | владелец `ROOT` или `laiot` | пользователь служб и владелец `var` |
| `--group NAME` | основная группа пользователя | группа владельца и сокета |
| `--php-bin PATH` | PHP из `PATH` | CLI PHP для проверки и всех создаваемых юнитов |
| `--socket PATH` | `/run/laiot/agent.sock` | Unix-сокет агента |
| `--systemd-dir PATH` | `/etc/systemd/system` | каталог юнитов |
| `--agent-config PATH` | `/etc/laiot/agent.json` | конфигурация агента |
| `--start` | выключено | сразу запустить ядровые службы, а не только включить |
| `--force` | выключено | перезаписать существующие `agent.json` и юниты |
| `--dry-run` | выключено | напечатать команды, ничего не меняя |

`--dry-run` тоже требует root: скрипт проверяет реальные владельцев, права и
systemd. Он не создаёт каталоги, не пишет файлы и не вызывает `systemctl`.

## Что меняет скрипт

1. Создаёт каталоги данных и выставляет `0775` и владельца `USER:GROUP`:
   `var`, `var/log`, `var/cache`, `var/locks`. В раскладке releases
   дополнительно создаётся `ROOT/shared`, иначе systemd не запустит юнит с
   несуществующим путём в `ReadWritePaths`. Содержимое существующих
   каталогов скрипт не перебирает и не меняет.
2. Генерирует `--agent-config` (по умолчанию `/etc/laiot/agent.json`)
   со значениями root, user, group, socket, systemctl, unit_dir и
   `allowed_uid`. Файл получает владельца `root:GROUP` и права `0640`;
   каталог конфигурации — `0750`. Существующий файл без `--force` не
   перезаписывается: администратор мог его осознанно поправить.
3. Рендерит `laiot-agent.service`, `laiot-worker@.service` и
   `laiot-core@.service`, а также `laiot-update.service` из `deploy/systemd` и кладёт их в
   `--systemd-dir` с правами `0644 root:root`. Если юнит уже есть и
   отличается, без `--force` скрипт останавливается, а не оставляет службу
   со старыми путями.
4. Выполняет `systemctl daemon-reload`, включает и перезапускает
   `laiot-agent.service`, включает `laiot-core@queue`,
   `laiot-core@events`, `laiot-core@timeouts` и
   `laiot-core@maintenance`. С `--start` добавляет `--now`, то есть сразу
   запускает их. WebSocket включается как `laiot-core@websocket` тем же
   механизмом. Без `--start` службы стартуют при загрузке сервера.
5. Если найден юнит `php*-fpm.service`, печатает подсказку
   `systemctl reload`. Сам перезагружает FPM только с `--start`: без явного
   флага скрипт не трогает веб-стек.
6. Печатает путь к ключу установки и следующие шаги: `/install`,
   `var/install.key`, `systemctl status` и `journalctl` для
   `laiot-core@events`.

Скрипт не создаёт `.env`, не выполняет миграции, не создаёт администратора,
не пишет в базу и не меняет код приложения. Файл `.env` он только проверяет
на наличие и доступность записи.

WebSocket устанавливается штатной core-задачей `laiot-core@websocket`.
Проксирование nginx описано в [websocket.md](websocket.md); SSH-мастер
[install-server.sh](server-installer.md) настраивает его автоматически.

## Раскладка: прямой корень и releases

Скрипт определяет раскладку по наличию `ROOT/current`:

- **Прямая раскладка** — текущая рабочая: код лежит прямо в `ROOT`, данные в
  `ROOT/var`. Юниты адаптируются: `WorkingDirectory=ROOT`,
  `ExecStart=/usr/bin/php ROOT/bin/laiot ...`, `ReadWritePaths=ROOT/var`.
- **Раскладка releases** — код в `ROOT/current`, общие данные в
  `ROOT/shared`. Юниты рендерятся почти как в шаблонах:
  `WorkingDirectory=ROOT/current`, `ExecStart=.../current/bin/laiot ...`,
  `ReadWritePaths=ROOT/shared ROOT/current/var`.

| Строка юнита | Прямая раскладка | releases |
| --- | --- | --- |
| `WorkingDirectory` | `ROOT` | `ROOT/current` |
| `ExecStart` | `ROOT/bin/laiot` | `ROOT/current/bin/laiot` |
| `ReadWritePaths` | `ROOT/var` | `ROOT/shared ROOT/current/var` |
| Каталог данных | `ROOT/var` | `ROOT/current/var` (обычно ссылка на `ROOT/shared/var`) |

Шаблоны в `deploy/systemd` сами не меняются: подстановка выполняется в
скрипте. Сам системный установщик не переключает релизы. Обычная установка
остаётся прямой; [обновитель](updates.md) сохраняет её стабильные входы,
создаёт release-каталоги и атомарно переключает current. Постоянные данные
остаются по прежним путям; `.env` и var подключаются к каждому релизу.

## Права агента и сокет

Агент работает от root и принимает ограниченный набор команд systemd через
Unix-сокет. Сокет создаётся с правами `0660`, каталог `/run/laiot` — `0770`,
владелец `root:GROUP`. Доступ к сокету — административная возможность:
пользователь PHP должен входить в `GROUP`.

Разрешены ядровые задачи из `CoreWorker::TASKS`, полосы `events.<n>` и
`module.<id>` существующего SDK-модуля. WebSocket использует те же
`core.start/stop/restart/status` с `module: websocket`, без отдельных действий.
Произвольные имена юнитов и shell-команды не принимаются.

`worker.install` проверяет наличие защищённых юнитов `root:root` и возвращает
их пути. Он не копирует шаблоны из доступного пользователю приложения каталога:
иначе изменение шаблона давало бы root-права. Установку и обновление юнитов
выполняет `deploy/setup-ubuntu.sh` от root, автоматически вызываемый SSH-мастером.

В `agent.json` поле `allowed_uid` равно uid пользователя `--user`. Агент
сверяет uid peer'а, когда в PHP доступен `posix_getpeereid`; на части сборок
этой проверки нет, поэтому одного членства в группе недостаточно. Если
PHP-FPM работает под другим пользователем (например, `www-data`), панель
получит отказ `peer uid denied`. Варианты: запустить сайт под тем же
пользователем, что и службы, либо вручную изменить `allowed_uid` на uid
пользователя FPM. Скрипт выбирает владельца `ROOT`, если тот не root, — так
учётные записи чаще совпадают.

Поле `root` в `agent.json` указывает на каталог приложения (`ROOT` или
`ROOT/current`): агент ищет модули в `<root>/modules` и берёт оттуда шаблоны
юнитов. Поэтому в раскладке releases туда записывается `ROOT/current`, хотя
сами юниты устанавливает скрипт, а не действие `worker.install` агента.

## Порядок запуска

1. `laiot-agent.service` — первым: без него панель не управляет службами.
2. `laiot-core@queue` — очередь `default`.
3. `laiot-core@events` — обязателен: без него значения сохраняются, но
   история, журнал и OnChange отстают.
4. `laiot-core@timeouts` — созревшие таймеры.
5. `laiot-core@maintenance` — один процесс на установку, очистка по срокам.
6. `laiot-worker@<module>` — задачи SDK-модулей, включаются по мере
   необходимости через панель или агент.

`laiot-core@system-events` скрипт не включает: это отдельный генератор
событий времени, его запускают вручную, если он нужен. Подробности о типах
процессов и блокировках — [runtime.md](runtime.md).

## После установки

1. Откройте `https://<ваш-сайт>/install` и пройдите мастер: он запишет
   `.env`, выполнит миграции и создаст администратора.
2. Ключ установки лежит в `<app>/var/install.key`; прочитайте его по SSH или
   в файловом менеджере. В прямой раскладке это `ROOT/var/install.key`, в
   releases — `ROOT/current/var/install.key`.
3. Если скрипт запускали без `--start`, запустите ядровые службы после
   установки:

   ```bash
   systemctl start laiot-core@queue.service laiot-core@events.service \
     laiot-core@timeouts.service laiot-core@maintenance.service
   ```

4. Проверьте состояние и журнал:

   ```bash
   systemctl status laiot-agent.service
   systemctl status laiot-core@events.service
   journalctl -u laiot-core@events.service -n 100
   ls -l /run/laiot
   ```

## Что остаётся вручную

- **nginx и TLS.** Виртуальный хост, корень `public`, fastcgi на PHP-FPM и
  сертификат скрипт не настраивает: это инфраструктура хостинга.
- **PHP-FPM.** Пул и его пользователь задаются на хосте. Пользователь пула
  должен совпадать с `--user` (или с `allowed_uid`), иначе панель не сможет
  управлять службами. `pm.max_children` и
  `request_terminate_timeout` подбираются под нагрузку.
- **MariaDB и Redis.** Установка, база, пользователь БД, пароль и политика
  Redis (`noeviction` для блокировок worker) остаются администратору; доступы
  записываются через `/install` в `.env`.
- **FastPanel и подобные панели.** Они управляют nginx, FPM и сайтом и могут
  пересоздать виртуальный хост или пул. Скрипт не спорит с ними: после
  изменений в панели проверьте пользователя FPM и доступ к сокету агента.
- **Пользователь и владелец кода.** Скрипт не создаёт пользователя и не
  делает `chown` на файлы приложения. Каталог установки должен быть доступен
  пользователю на запись, иначе `/install` не сможет создать `.env`;
  скрипт проверяет это и предупреждает.
- **Зависимости и сборка.** `composer install` и `npm run build` выполняются
  до запуска служб; скрипт только предупреждает об отсутствии
  `vendor/autoload.php`.
- **Резервные копии, мониторинг, firewall и logrotate.** Вне границ скрипта.

## Ограничения

- Автоматического отката нет. Скрипт не создаёт резервные копии юнитов и
  `agent.json`; при `--force` прежние файлы заменяются. Откат — вручную.
- Релизами управляет [обновитель](updates.md), а не этот скрипт.
  `laiot-update.service` устанавливается под пользователем сайта и
  запускается по подтверждённой операции, без enable при загрузке сервера.
- Скрипт не создаёт системного пользователя, базу и `.env`. Это сделано
  намеренно: такие действия требуют решения администратора.
- Права меняются только у самих каталогов `var`, без рекурсии. Если
  приложение раньше запускали от root, файлы внутри `var` могут остаться
  root-овыми; проверьте их владельца вручную.
- Один сервер — одна установка. Файловые блокировки и сокет не рассчитаны
  на несколько хостов или независимых каталогов releases.
- `allowed_uid` описывает одного пользователя. Разным пользователям панели и
  служб нужна ручная настройка.
- Юниты FPM ищутся по шаблону `php*-fpm.service` в стандартных каталогах
  systemd; нестандартный юнит или управление из панели хостинга может не
  найтись, и подсказка не появится.
- Скрипт не проверяет корректность кода, схемы базы и `.env` — это задачи
  `doctor`, `health` и установщика. См. [console.md](console.md) и
  [configuration.md](configuration.md).
- Поддерживается только Linux с systemd. Windows и macOS не являются
  целевой платформой, хотя синтаксис скрипта можно проверить через
  `bash -n`.

## Диагностика

```bash
systemctl status laiot-agent.service
journalctl -u laiot-agent.service -n 100
systemctl status laiot-core@events.service
journalctl -u laiot-core@events.service -f
php bin/laiot doctor
php bin/laiot health
```

Если панель не управляет службами, проверьте владельца и права сокета,
членство пользователя FPM в группе и `allowed_uid`. Если службы падают после
перезагрузки, проверьте `ReadWritePaths` и наличие каталогов `var` и
`shared`.
