# Обновление системы

Раздел **Система → Сервис → Обновление системы** (`/admin/updates`)
доступен с правом `settings.manage`: текущая версия, каналы `main`/`beta`,
описание релиза, проверки и подтверждение последствий. Интерактив — Yoyo;
обращение к GitHub происходит по явной проверке обновлений.

«Проверить обновления» каждый раз запрашивает все страницы каталога GitHub
с перепроверкой HTTP-кэша и заменяет сохранённый список только после полного
успеха. Карусель показывает 10 последних доступных выпусков выбранного канала
от новой версии к старой и отдельную карточку установленной версии без дублей.
Есть свайп, стрелки, счётчик и переход «Моя версия»; автоматического листания нет.
Сохранённые локальные версии учитываются в списке, текущая карточка доступна
при любом канале и не предлагает повторно устанавливать саму себя.
Заголовок карточки занимает две строки: номер, затем дата и размер архива.
Карточка содержит краткий список изменений и ссылку
на GitHub. «Читать полностью» открывает безопасно отформатированное описание
релиза в модальном окне без сетевого запроса. Проверка окружения и установка
запускаются отдельно. Если GitHub сократил описание, ссылка на полный
`CHANGELOG.md` остаётся в тексте релиза.

Получение списка, смена канала, проверка релиза и запуск имеют индикаторы
загрузки; повторные действия блокируются до ответа. При ошибке HTTP или
соединения блокировка снимается и показывается Notify.
Мини-игры на странице выбора релиза нет.

Версия поставки читается из `release.json`. До первого номерного выпуска
начальная версия — `0.0.0`; выбранный канал задаёт идентификатор
`beta-0.0.0` либо `main-0.0.0`. Отсутствующая версия не становится искусственно
новее первого релиза. Номер установленного релиза сохраняет приоритет.

## Источник и выпуск

По умолчанию источник — `laiot-smarthome/laiot`. В настройках или `.env`
можно выбрать свой публичный форк:

```dotenv
UPDATE_REPOSITORY=laiot-smarthome/laiot
UPDATE_CHANNEL=beta
```

Репозиторий задаётся как `owner/repository` или HTTPS-адрес GitHub.
Канал — начальный фильтр страницы; версии сравниваются как semver
отдельно от канала. Авторизация приватных репозиториев пока не реализована.

### Автоматический выпуск

В последний коммит перед push в `main` или `beta` добавьте одну пометку
`[release: 0.0.3]`. Канал берётся из ветки: получится `main-0.0.3`
или `beta-0.0.3`. Допустим номер с суффиксом, например
`[release: 0.1.0-beta.1]`. Обычные коммиты без пометки релиз не создают.
Проверяется именно последний коммит push; при squash пометка должна
остаться в итоговом сообщении.

```bash
git commit -m "[release: 0.0.3] Обновление системы"
git push origin beta
```

Альтернативы: push готового тега `main-0.0.3` / `beta-0.0.3` либо
**Actions → Build release → Run workflow** с веткой `main`/`beta` и полем
`version` без префикса канала. Для кнопки ручного запуска workflow должен
также присутствовать в default branch репозитория.

`.github/workflows/release.yml` проверяет принадлежность коммита ветке,
запускает `composer check`, проверки документации, frontend и release-helper,
собирает ассеты и устанавливает production Composer-зависимости.
Тег создаётся автоматически на проверенном commit. Сначала создаётся
черновик с файлами, затем он публикуется; незавершённый черновик updater
не видит. Beta помечается prerelease, main — стабильным Latest.
Публикуются:

- `laiot.zip`: код, vendor, встроенные модули и готовая статика;
- `laiot-release.json`: номер, канал, commit, требования PHP/расширений,
  манифесты встроенных модулей, размер архива и SHA-256.
- `CHANGELOG.md`: все заголовки и полные описания коммитов после предыдущего
  опубликованного выпуска своего канала, со ссылками на коммиты и сравнение.

Черновики и другая ветка не задают начало истории. Ранее опубликованный
обычный числовой тег учитывается, если его `target_commitish` совпадает
с каналом. Без предыдущего выпуска включается вся история. Если описание
не помещается в лимит GitHub, на странице остаются последние 50 заголовков
и ссылка на полный `CHANGELOG.md`; файл содержит все коммиты.

Сборка — `php bin/laiot release:build <tag> --output <directory>`.
Требования встроенных модулей проверяются относительно номера выпуска
до упаковки: архив с несовместимыми требованиями не публикуется.
В поставку не входят `.env`, `var`, сторонние модули и их опубликованные
ассеты. На сервере Composer и npm при обновлении не запускаются.
Номерный релиз не перезаписывается. Если другой форк использует уже
сохранённый номер для другого commit, потребуется новый номер.

### Настройки GitHub

В **Settings → Actions → General** разрешите используемые actions:
`actions/checkout@v7`, `actions/setup-node@v7`, `shivammathur/setup-php@v2`.
Можно выбрать **Allow all actions and reusable workflows** либо ограниченный
список с этими тремя actions. Workflow permissions можно оставить
**Read repository contents and packages permissions**: выпуск явно
запрашивает только `contents: write`. Разрешение создавать/одобрять PR
ему не требуется. Секреты, PAT, SSH-ключи и собственный runner не нужны:
используются встроенный `GITHUB_TOKEN` и GitHub-hosted Ubuntu.

Workflow, helper `.github/release.mjs` и новая команда npm должны быть
отправлены в нужные ветки вместе с кодом приложения. Создавать релиз вручную
в интерфейсе GitHub не требуется. Существующие опубликованные релизы и
черновики с таким номером не перезаписываются. При ошибке публикации
проверьте журнал **Actions → Build release**; незавершённый черновик требует
решения владельца репозитория перед повторным использованием номера.

## Код и постоянные данные

Новый релиз распаковывается в **пустой** `releases/<id>`: удалённых из
исходников файлов в рабочей версии нет, ручной список удалений не нужен.
Старые release-каталоги сохраняются для возврата. `current` переключается
атомарной заменой ссылки.

Прямая установка сохраняет стабильные `public/index.php`, `bin/laiot`
и `bootstrap/app.php`, передающие выполнение current. Первоначальный код
сохраняется как локальный релиз, первоначальная статика — в
`var/updates/original-assets`. Веб-корень и пути служб менять не нужно.

`var`, `.env`, APP_KEY и исходный каталог сторонних модулей общие;
`var/updates/layout.json` фиксирует их пути. ModuleManager обнаруживает
сторонние модули в постоянном каталоге. Их код и отдельные SQLite-БД
не заменяются. Публичные ассеты установленных модулей публикуются из
текущих исходников в каталог проверяемого релиза без lifecycle-хуков.

## Проверки и операция

Нужны Linux, PHP 8.2+ с расширениями релиза, MySQL/MariaDB и клиентские
утилиты `mariadb-dump`/`mysqldump`, `mariadb`/`mysql`. Проверяются место,
права, ключ, БД, агент, требования и зависимости модулей. PHP/CLI работают
под пользователем сайта — владельцем `.env` и var; root запрещён.
При возврате дополнительно сверяются версии модулей со снимком.

`deploy/setup-ubuntu.sh` устанавливает `laiot-update.service` под
пользователем сайта. Существующие службы нужно привести к актуальным
шаблонам этим скриптом; updater не пишет root-юниты. Агент принимает
фиксированные действия, без произвольных shell-команд. Служба обновления
не включается на каждом boot, а запускается по подтверждённой операции.

1. Повторить проверки и сохранить прежний код.
2. Скачать архив, проверить SHA-256, пути, типы файлов и размер;
   подготовить каталог и проверить загрузку PHP-зависимостей.
3. Закрыть запись, остановить фоновые службы, дождаться HTTP-запросов.
4. Сохранить последний снимок MySQL исходного релиза.
5. Применить миграции впервые устанавливаемой новой версии либо
   восстановить снимок выбранного сохранённого релиза.
6. Сбросить только прикладной кэш остановленной установки; проверить
   ядро, схему, администратора и кэш; переключить код,
   запустить нужные службы, открыть запись и перезапустить агент.

Понижение версии без её сохранённой БД запрещено. Обратные миграции
поверх новой схемы не выполняются.

## Один снимок БД на релиз

`var/backups/<id>.zip` содержит `database.sql` и `snapshot.json`:
версию, дату, версии/состояния модулей, список служб, идентичность БД,
отпечаток ключа и SHA-256 дампа. Пароля и самого APP_KEY в описании нет.

При уходе с A последний снимок A заменяется только после полной записи,
проверки и синхронизации новой копии. Дамп с описанием заменяются одним
файлом. Незавершённая копия не становится точкой восстановления.
Повтор после сбоя не перезаписывает исходный снимок частичной миграцией.

Восстановление очищает таблицы, представления, routines и events
**выделенной БД приложения**, затем импортирует проверенный дамп.
Встроенные модули входят в эту MySQL. Отдельные SQLite сторонних модулей
и пользовательские файлы остаются текущими. Более новые пользовательский
код, привязки, настройки, история и другие записи MySQL будут потеряны:
интерфейс показывает дату и требует подтверждения.

## Аварийное восстановление

`var/updates/operation.json` хранит этапы независимо от БД. Процесс
удерживает flock; после перезагрузки незавершённая операция без
блокировки определяется как прерванная. PID для этого не используется.

`/admin/updates/recovery` работает **до Composer, boot и БД**. Показывает
этап, журнал и выбор «Попробовать ещё раз» / «Вернуть прежнюю версию».
Здесь же сразу доступна локальная «Змейка», без раскрывающегося блока.
Прогресс обновляется отдельно от игры, без перезагрузки страницы;
запрос состояния требует ту же cookie и не возвращает ключи доступа.
Запуск из панели устанавливает отдельную HttpOnly/SameSite-cookie.
Если cookie потеряна, введите на аварийной странице ключ из серверного
`var/updates/recovery.key`. Ключ не передаётся в URL. POST проверяет
CSRF, идентичность операции и отдельное подтверждение последствий.

Повтор сначала возвращает проверенные исходные код/БД, затем заново
выполняет обновление. Возврат восстанавливает прежние код/БД и службы.
Если полный успех уже зафиксирован, повтор завершает открытие системы
без нового импорта. Чистая установка сама не запускается. После ошибки
запись остаётся закрытой до решения пользователя, если пауза уже началась.

```bash
php bin/laiot update:status
```

Эта диагностика не требует boot приложения. Параметры —
[консоль](console.md), службы — [развёртывание](deploy.md),
изоляция проверок — [тестирование](testing.md).

Копия на том же диске не защищает от потери диска; для этого нужна внешняя
резервная копия. Возврат БД не отменяет отправленные устройствам команды.
