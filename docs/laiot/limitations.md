# Ограничения текущего ядра

Состояние сверено с исходниками ветки LaIOT на 2026-10-26 после переноса
ядровых страниц (`7cae516e`). Этот список не заменяет
[мастер-план](../todo/laiot.md): здесь зафиксированы границы поведения,
которые особенно важно не представлять как завершённые функции.

## Конфигурация и доступ

- `bootstrap/app.php` запрашивает `APP_TIMEZONE`, которого нет в схеме
  Config. На этом пути применяется `Europe/Moscow`, независимо от такого
  ключа в `.env`. Общий Config отдельно понимает `TIMEZONE`.
- Основной bootstrap выбирает MySQL; Laravel-подобные `DB_CONNECTION`,
  `SESSION_DRIVER`, `QUEUE_CONNECTION` не переключают рабочие реализации.
  Настройки тестов действуют через прямую сборку Application.
- `Authorization` использует резервные сессионные права при пустых
  разрешениях/ошибке их чтения. Это не строгая модель отказа при сбое БД.
  Middleware `auth` отдельно отзывает сессии по `is_admin` и паролю.
- API-токен требует существующего неудалённого владельца. Снятие флага
  `is_admin` закрывает панель, но сохраняет доступ по токену: этот флаг
  не является общим признаком блокировки учётной записи.
- `user:create --admin` назначает роль `admin` и объект Users; пароль
  пока принимается аргументом командной строки.

## Пользовательский PHP

Методы, сценарии и PHP-webhook — доверенный код через временный файл и
`include`, не sandbox. Перед сохранением код разбирается штатным парсером
PHP (`PhpSyntaxValidator`), поэтому синтаксическая ошибка в базу не попадает,
но это проверка, а не изоляция исполнения. Выключенный флажок «Подключать
ядро» запускает сценарий отдельным php-процессом без bootstrap: функции ядра
там не определены, но процесс работает под тем же пользователем и с тем же
доступом к файлам и сети — это другой режим загрузки, а не sandbox.
Объявленного в старых планах `CodeGuard` и команды `legacy:scan` в новом
runtime нет. Запрет SQL/shell — правило разработки, а не техническая гарантия,
что пользовательский PHP не сможет их вызвать.

`$this` в методе — `MethodContext` объекта: короткий доступ к свойствам,
истории, другому методу и уведомлениям. Это не объект MajorDoMo из alpha и
не compatibility-слой: старые методы объекта и глобалы вроде `$this->setProperty()`
не поддерживаются. `$params` и обёртки `gg/sg/callMethod` остаются.
Полная совместимость пользовательских автоматизаций alpha не заявляется;
наследование свойств и методов классов работает в модели дома.

Сценарии выполняются через `CodeRunner` без привязки `$this`: у сценария нет
объекта. Им доступны `$params` и глобальные обёртки; контекст объекта — только
у метода.

Запуски сценариев по событиям обслуживает один `core-worker queue`, поэтому
они идут последовательно; отдельных полос для сценариев нет. Тайм-аут 10
секунд действует только в режиме без ядра, а сценарий с ядром может задержать
очередь. Ручной запуск из панели идёт HTTP-запросом и параллелится свободными
процессами PHP.

`say(string $message, int $importance = 5): array` сохраняет уведомление
`info` с важностью 0–10. Источник определяется автоматически по вызывающему
модулю или исполнителю кода. При важности от `SAY_MINIMUM_IMPORTANCE`
включительно (по умолчанию 5) атомарно ставит `system.say` подписчикам в
фоновые очереди; ниже порога — только журнал. Возврат подтверждает запись
и постановку заданий при достижении порога, а не доставку пользователю.
Окно повторов по умолчанию час, настраивается через
`NOTIFICATIONS_DUPLICATE_WINDOW`; повышение важности обходит окно,
лимит 10 непрочитанных снят. Требуется миграция
`2026_10_29_000001_add_notification_importance.php`. Каналы
Telegram, push и речь пока не реализованы. Старые `level`, `member_id`
и `shoutbox_latest()` отсутствуют. Контракт — [notifications.md](notifications.md).

## API и маршрутизация

У API нет единого конверта успеха/ошибки и завершённого API v2/OpenAPI.
Примеры форматов собраны в [api.md](api.md).

WebSocket — только исходящий: входящие кадры
закрывают соединение. Тикет выдаётся администратору и перечисляет каналы
без отдельной проверки права на каждое свойство; гранулярный доступ к
объектам пока не реализован. Каждый процесс Workerman читает общий outbox
`websocket_events` сам; межпроцессного брокера нет. Системные события идут
в канал `system` всем подключениям. Подробности и запуск —
[websocket.md](websocket.md).

В kernel зарегистрированы `/api/create` и `/api/{id}/...`, однако внешняя
маршрутизация CRUD webhook пока не проверена: alpha nginx и dev server
удалены, нового стенда нет. Тест, вызывающий Application напрямую, эту
границу не проверяет.

Legacy `public/api.php` удалён вместе с alpha-runtime. `/api/v1/*` и страница
webhook идут через `public/index.php`; отдельного входа для старых `/api/*`
больше нет. Работа под URL-подкаталогом требует отдельной проверки: новые
маршруты и ссылки в значительной части заданы от `/`.

## Кэш и фоновая работа

- `clear()` ограничивает префикс только для Redis; остальные драйверы
  очищают своё хранилище через Repository. Прикладной кэш включает
  worker-lock/heartbeat: очистка затрагивает и фоновые процессы.
- Production-фоновое состояние предполагает Redis, но класс состояния
  принимает общий CacheStore и сам не запрещает другой драйвер.
- Redis-lock имеет TTL 120 секунд. Для worker одной установки используется
  также файловая блокировка на всё время процесса; разные серверы и отдельные
  каталоги releases не защищены ею от параллельной работы.
- Без `pcntl` задача модуля исполняется в текущем процессе без fork-timeout.
  Linux/systemd и live Redis должны проверяться отдельно от Windows/array.
- Очередь допускает повторное выполнение; токен резервации защищает от
  запоздавшего подтверждения другого воркера. Таймеры имеют такую же аренду
  (`claim_token`), но без счётчика попыток и failed-политики: после ошибки
  запись просто снова доступна. Retention (`db:prune`) удаляет только
  выполненные/отменённые таймеры, поэтому «застрявший» таймер не исчезает
  сам.
- Изменения свойства асинхронны: запись сохраняет значение и задание, а
  OnChange, история и доставка выполняются в `core-worker events`. События
  разложены по полосам: одно свойство всегда в одной полосе, параллельность
  даёт запуск `core-worker events.<n>` на полосу. Автоматического
  масштабирования и смены числа полос на лету нет. Без запущенного events
  история и журнал отстают, а методы не выполняются.
- Доставка подписанным модулям уходит отдельным заданием в `module.<id>` и
  выполняется `worker <id>`, а не процессом events: медленный подписчик
  задерживает только свой модуль. Подписку на свойство выбирает пользователь
  на странице `/admin/modules/<id>/settings`; отдельного выбора свойств внутри
  карточки объекта пока нет.
- Настройки модуля описываются манифестом и хранятся в
  `module_registry.settings`; форма общая. Произвольные данные, не описанные
  в схеме, модуль хранит в своей `ModuleDb`, а не в реестре. Core-модуль —
  исключение: реестр настроек для него закрыт, поэтому MQTT хранит параметры
  брокера в `module_mqtt_settings` и рисует страницу настроек сам
  ([mqtt.md](mqtt.md)).
- MQTT: MQTT 3.1/3.1.1, один процесс приёма, нет импорта таблиц alpha.
  Сторонние модули подключаются через реестр `Integrations` и сами отвечают за
  очередь и worker; общего брокера внутри процесса нет. HTTP-команды из alpha
  (`PATH_WRITE` с `http://`) и «последние 20 записей на топик» не перенесены:
  журнал чистится по сроку. Живой брокер и end-to-end задержка в
  изолированных тестах не проверяются; тест модуля работает без сети.
- Zigbee: собственного MQTT-клиента нет, модуль зависит от MQTT и скрывается
  при его выключении. Импорт таблиц alpha `zigbee`/`zigbeedev` — отдельная
  операция, старые данные не читаются. Журнал — до 1000 записей на экземпляр,
  карта сети только пишется в журнал, изображения устройств с внешнего сайта
  не загружаются. Живой брокер и Zigbee2MQTT проверяются на стенде, а
  `ZigbeeModuleTest` работает на SQLite без сети. Подробности —
  [zigbee.md](zigbee.md).
- Файловые миграции SDK получают основное соединение, не отдельный
  SQLite-файл ModuleDb. Выбор storage.driver и выбор соединения миграции
  пока не одно действие; детали — в [sdk.md](sdk.md).

## Что ещё остаётся планом

Marketplace и полный перенос оставшихся интеграций.
[Обновление](updates.md) реализовано для одной Linux-установки с MySQL,
общими var/.env и номерными публичными релизами; приватные GitHub-репозитории
и несколько серверов не поддерживаются. Снимки находятся на том же диске,
отдельные SQLite сторонних модулей и команды устройствам не откатываются.
Установщик уже есть — страница
`/install` и команда `install` пишут `.env`, применяют миграции и создают
администратора ([install.md](install.md)); systemd-часть остаётся отдельной
операцией ([deploy.md](deploy.md)). Права из `module.json` регистрируются
при install/enable, но автоматически никому не выдаются, кроме роли admin
(`*`); выдача остальным ролям — вручную. SDK доверяет модулям: ModuleDb
ограничивает API доступа, `module:check` ищет legacy-вызовы, но не
изолирует PHP-процесс.

Alpha-runtime удалён из ветки: `lib/`, `templates/`, `scripts/`, `languages/`,
`cms/`, alpha-модули, `packages/phpmqtt` и старые входы `install.php`,
`api.php`, `404.php`, `cycle.php`, `dev_server.php`. Ветка `alpha` остаётся
источником старой реализации и данных для переноса. Неперенесённые
интеграции и импорт данных проектируются заново на новом ядре. Локальный
Docker-стенд для просмотра есть, production-развёртывания пока нет.

Актуальные результаты запусков отмечаются в журнале проверки, а не
выводятся из старого зелёного чекбокса. При изменении перечисленного кода
обновляйте этот документ вместе с профильным руководством.
