# Работа с MyDoMo

## Порядок чтения

1. [README](README.md) — карта реализованного и незавершённого.
2. [Архитектура](architecture.md) и [ограничения](limitations.md).
3. [Мастер-план](../todo/mydomo.md) — решения и следующий этап.
4. Профильный документ и непосредственно затронутый код.

Не сканировать весь проект перед небольшой задачей. Версии проверять в
относящихся к задаче composer/package-файлах. Новый код рассчитан на
PHP 8.2+, Illuminate 12 components; это не full-stack Laravel/Livewire.

## Границы кода

- Ядровые разделы — `src/Http/Controllers/Core` и `resources/views/pages`;
  регистрация в `routes`, меню в CoreSections. Для них не создавать
  module.json, ModuleDb и install hooks.
- MQTT, Zigbee и внешние интеграции — SDK-модули в `modules/core/<id>`
  либо `modules/<id>`. Реализацию интеграции не переносить в ядро ради меню.
- Ядро содержит универсальные сервисы; module-specific код остаётся в
  своём модуле. Страницы и интеграционные модули — разные понятия.
- Новый код не подключает SQLSelect, mysqli, legacy loader, JTemplate,
  старые module.class.php и alpha-таблицы. `Foundation\Config` — простой
  `.env`-парсер, а не повод возвращать старые runtime-слои.
- Пользовательские методы/скрипты — доверенный PHP; CodeGuard и sandbox
  ещё не реализованы. Не обещать их по названию Safe в helper.

После переноса старый код удаляется; редиректов со старых URL и
runtime-адаптеров совместимости не добавляем. Отдельный импорт данных,
если понадобится, не должен подменять чтение новой схемы.

## Alpha — смысл, а не совместимость

Поведение alpha смотрим поверхностно: что функция должна делать для
пользователя. Сигнатуры, флаги и структуры alpha не переносим — `$noLinked`,
`LINKED_MODULES`, `_chain`, `view_mode` и подобные артефакты остаются в старой
ветке. Совместимость пользовательского кода alpha не цель проекта.

Внутренний API проектируем явно: состояние и контекст держит сервис, а не
магический аргумент вызывающего; параметр получает смысл, а не номер позиции.
Правило проверяется тестом и фиксируется в профильном документе вместе с
кодом.

Пример: доставку свойства модулям alpha включала флагом `$noLinked`, в новом
ядре эхо гасит контекст обработчика в сервисе записи, а публичная `sg()` не
имеет служебных аргументов.

Для SDK действует то же правило: настройки описываются схемой `settings` в
`module.json` и читаются через `$context->settings()`, подписки на свойства
ставятся через `$context->subscriptions()`. Модуль не создаёт свою таблицу
настроек и не вставляет строки в `property_subscriptions` напрямую.

## Интерфейс и доступ

Сохраняется визуал панели alpha, реализация — Blade, Alpine, Yoyo там,
где он уже используется. Компоненты `x-md.*` и классы `md-*`, локальные
ассеты через существующую npm-сборку. Старый MDJUI PHP и jQuery не являются
зависимостями нового интерфейса. Визуальные правила старой дизайн-системы
можно читать как источник оформления, не runtime-контракт.

Ссылки и кнопки панели не подчёркиваются: акцент дают цвет, значок и фон.
Для ссылок используйте `x-md.link` (`primary`, `muted`, `subtle`, `danger`,
`hint`, `action`); пунктир допустим только у `hint` для подсказки. Для
кнопок и форм — `x-md.button`. Не добавляйте `text-decoration` в разметку
и не подчёркивайте кнопки-ссылки. Контракт — [ui-kit.md](ui-kit.md#ссылки).

Изменяющие маршруты требуют серверной валидации, auth/нужного can: и CSRF.
Не считать auth автоматической проверкой каждого права или манифест
permissions готовой политикой. Доступ и текущие исключения —
[authentication.md](authentication.md).

### Единая валидация входных данных

Для новых и изменяемых форм, HTTP/API-входов, Yoyo и SDK использовать
`illuminate/validation` через общий `Illuminate\Contracts\Validation\Factory`
из DI. Готовые правила и `Illuminate\Validation\Rule` имеют приоритет:
не писать вручную проверки required, string, integer, email, min/max,
in, unique, exists и вложенных массивов, уже доступные в пакете.

Не создавать собственные движки валидации, базовые валидаторы и парсеры
правил. Повторяемый набор правил хранить в одном прикладном классе и
использовать из разных точек входа. Собственное правило допустимо только
для предметной проверки, которой нет в Illuminate; повторяемую проверку
оформлять через штатный контракт `ValidationRule`.

В сервис передавать проверенные данные (`validated()`), а не весь запрос.
Авторизация, CSRF, инварианты домена, транзакции и ограничения БД остаются
отдельными проверками. Схемы настроек SDK не дублировать: при доработке
их проверки использовать общий валидатор за существующим контрактом.
Уже работающие формы переносить при соответствующем изменении, сохраняя
их поведение. Подключение пакета само не включает Laravel FormRequest
и `$request->validate()`. Примеры и обработка ошибок —
[validation.md](validation.md).

### Yoyo вместо самописных эндпоинтов

Любой интерактивный блок страницы (фильтры, панели, drawer'ы, поиск,
переключение периода) делается Yoyo-компонентом в `src/Yoyo` и шаблоном
`resources/views/yoyo/<name>.blade.php`. Действия — `yoyo:get`/`yoyo:post`
через общий `/yoyo`, состояние — публичные свойства компонента.

- Имя компонента `kebab-case` автоматически разрешается в класс
  `MajorDoMo\Yoyo\StudlyCase`; список `registerComponent` вручную не ведём.
- Отдельный JSON-эндпоинт для UI-блока — ошибка: данные считает сервис,
  компонент рендерит их на сервере.
- `/api/v1/panel/*` остаётся только для виджетов оболочки, которые живут
  вне Blade-страницы (поиск в шапке, колокольчик), и для внешнего API.
- Примеры: `property-history` (история с графиком), `events-table`
  (фильтры журнала событий).

## Сервисы, конфигурация и CLI

Секреты, которые нужно расшифровывать (токены и пароли интеграций), хранить
через общий Illuminate Encrypter. Модели от `Database\Model` используют
штатные encrypted-casts, секретные поля включаются в `$hidden`. Не писать
свои шифраторы/casts и не возвращать исходный текст при ошибке расшифровки.
APP_KEY создаётся установщиком автоматически и не меняется при повторе;
в обычном boot генерация ключа запрещена. Пароли пользователей остаются
хешами. Подробности — [encryption.md](encryption.md).

Сохраняемые файлы ядра — через `Files\LocalFiles` из DI, файлы SDK —
только через `$context->files()`. Корни: `var/files/core` и
`var/files/modules/<id>`. Не писать данные в исходники модуля, не выдавать
модулю общий диск или абсолютные пути. Удаление модуля удаляет его файлы
и без `--purge`; выключение их сохраняет. Пути и символические ссылки
проверяет общий файловый сервис, не дублировать собственные файловые
обёртки в модулях. Контракт — [files.md](files.md).

Значения свойств менять через PropertyValueService; не писать в таблицу
в обход истории, событий и OnChange. Запись свойства асинхронна: значение и
задание `property.changed` сохраняются в одной транзакции, а OnChange,
история и доставка выполняются в `core-worker events`. Не вызывать
обработчик события синхронно из записи и не обходить очередь в коде ядра.
Feature-тест, проверяющий журнал/историю/подписчика, явно дренит очередь
через `DrainsEvents`. Использовать DI и опубликованные
сервисы вместо новых глобалов. Публичные helpers — в
`src/Support/helpers`, сигнатуры — в [functions.md](functions.md).

Сборка зависимостей — сервис-провайдеры `src/Foundation/Providers`, список
в `config/providers.php`. Новую подсистему подключать через register/boot,
не возвращать подробную настройку сервисов в Application. Порядок и
singleton-состояние проверять по [providers.md](providers.md).

Конфигурация — `.env` + `Foundation\Config`; модули читают свои параметры
через `$context->settings()`, а не `getenv`/`define`. Нельзя описывать новый
.env-ключ, не проверив bootstrap и место применения. Подробнее —
[configuration.md](configuration.md).

CLI нового ядра: класс в `src/Console`, регистрация в `bin/mydomo`.
Не добавлять отдельный исполняемый скрипт для каждой операции. Основной
вход, аргументы и эффекты — [console.md](console.md).

## Документация и проверка

- Результаты действий админки (успех, ошибка, предупреждение) показывать
  только через Notify: `x-md.notify` в Blade, `dispatchBrowserEvent('md:notify', ...)`
  в Yoyo или `$store.mdToasts.push()` в Alpine. Для POST/redirect использовать
  одноразовую сессию через `PanelRenderer::redirect()`; текст в GET запрещён.
  Не добавлять баннеры результата в контент страницы. Ошибки
  валидации остаются также у полей; постоянные состояния и справочные блоки
  могут использовать `x-md.alert`. Правила — [ui-kit.md](ui-kit.md).
- При изменении CLI обновлять [console.md](console.md) в том же изменении;
  `ConsoleDocumentationTest` проверяет реестр, описания и параметры.

- Публичный контракт обновлять в профильном документе в том же изменении.
  functions.md остаётся индексом обёрток, а не копией всех руководств.
- В README менять статус только после проверки кода. Планируемое помечать
  явно; старые результаты запуска оставлять датированными снимками.
- В мастер-плане фиксировать факт, проверку и оставшуюся работу.
- Не менять код ради соответствия устаревшему тексту; сначала сверить
  решение владельца и текущую реализацию.

Для Markdown достаточно `php tests/docs_quality_smoke.php`, проверки
путей/ссылок/примеров. Для кода — подходящие изолированные тесты и
`composer check`; frontend — node --check и npm run build.

Тесты не подключают рабочий bootstrap/.env. SQLite и безопасные драйверы
подготавливаются до запуска; Linux-процессы и systemd проверяются в Linux.
Docker — только локальный стенд для просмотра; production-инструкцией он не
является. `health`, `doctor`, миграции и worker используют сервисы установки
и не являются заменой изолированному тестированию.

Изменения существующих файлов другого агента сохранять. Не создавать
коммит, если его не просили; при коммите код, документация и актуальные
отметки плана должны соответствовать друг другу.
