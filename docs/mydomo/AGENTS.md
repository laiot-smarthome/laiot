# Работа с MyDoMo

## Порядок чтения

1. [README](README.md) — карта реализованного и незавершённого.
2. [Архитектура](architecture.md) и [ограничения](limitations.md).
3. [Мастер-план](../todo/mydomo.md) — решения и следующий этап.
4. Профильный документ и непосредственно затронутый код.

Не сканировать весь проект перед небольшой задачей. Версии проверять в
относящихся к задаче composer/package-файлах. Новый код рассчитан на
PHP 8.2+, Illuminate 12 components; это не full-stack Laravel/Livewire.

## Границы кода

- Ядровые разделы — `src/Http/Controllers/Core` и `resources/views/pages`;
  регистрация в `routes`, меню в CoreSections. Для них не создавать
  module.json, ModuleDb и install hooks.
- MQTT, Zigbee и внешние интеграции — SDK-модули в `modules/core/<id>`
  либо `modules/<id>`. Реализацию интеграции не переносить в ядро ради меню.
- Ядро содержит универсальные сервисы; module-specific код остаётся в
  своём модуле. Страницы и интеграционные модули — разные понятия.
- Новый код не подключает SQLSelect, mysqli, legacy loader, JTemplate,
  старые module.class.php и alpha-таблицы. Config пока общий, но это не
  разрешение использовать остальные старые runtime-слои.
- Пользовательские методы/скрипты — доверенный PHP; CodeGuard и sandbox
  ещё не реализованы. Не обещать их по названию Safe в helper.

После переноса старый код удаляется; редиректов со старых URL и
runtime-адаптеров совместимости не добавляем. Отдельный импорт данных,
если понадобится, не должен подменять чтение новой схемы.

## Интерфейс и доступ

Сохраняется визуал панели alpha, реализация — Blade, Alpine, Yoyo там,
где он уже используется. Компоненты `x-md.*` и классы `md-*`, локальные
ассеты через существующую npm-сборку. Старый MDJUI PHP и jQuery не являются
зависимостями нового интерфейса. Визуальные правила старой дизайн-системы
можно читать как источник оформления, не runtime-контракт.

Изменяющие маршруты требуют серверной валидации, auth/нужного can: и CSRF.
Не считать auth автоматической проверкой каждого права или манифест
permissions готовой политикой. Доступ и текущие исключения —
[authentication.md](authentication.md).

### Yoyo вместо самописных эндпоинтов

Любой интерактивный блок страницы (фильтры, панели, drawer'ы, поиск,
переключение периода) делается Yoyo-компонентом в `src/Yoyo` и шаблоном
`resources/views/yoyo/<name>.blade.php`. Действия — `yoyo:get`/`yoyo:post`
через общий `/yoyo`, состояние — публичные свойства компонента.

- Имя компонента `kebab-case` автоматически разрешается в класс
  `MajorDoMo\Yoyo\StudlyCase`; список `registerComponent` вручную не ведём.
- Отдельный JSON-эндпоинт для UI-блока — ошибка: данные считает сервис,
  компонент рендерит их на сервере.
- `/api/v1/panel/*` остаётся только для виджетов оболочки, которые живут
  вне Blade-страницы (поиск в шапке, колокольчик), и для внешнего API.
- Примеры: `property-history` (история с графиком), `events-table`
  (фильтры журнала событий).

## Сервисы, конфигурация и CLI

Значения свойств менять через PropertyValueService; не писать в таблицу
в обход истории, событий и OnChange. Использовать DI и опубликованные
сервисы вместо новых глобалов. Публичные helpers — в
`src/Support/helpers`, сигнатуры — в [functions.md](functions.md).

Сборка зависимостей — сервис-провайдеры `src/Foundation/Providers`, список
в `config/providers.php`. Новую подсистему подключать через register/boot,
не возвращать подробную настройку сервисов в Application. Порядок и
singleton-состояние проверять по [providers.md](providers.md).

Конфигурация — Config и схема ключей; не добавлять getenv/define в модули.
Нельзя описывать новый .env-ключ, не проверив schema и место применения.
Подробнее — [configuration.md](configuration.md).

CLI нового ядра: класс в `src/Console`, регистрация в `bin/mydomo`.
Не добавлять отдельный исполняемый скрипт для каждой операции. Основной
вход, аргументы и эффекты — [console.md](console.md).

## Документация и проверка

- Публичный контракт обновлять в профильном документе в том же изменении.
  functions.md остаётся индексом обёрток, а не копией всех руководств.
- В README менять статус только после проверки кода. Планируемое помечать
  явно; старые результаты запуска оставлять датированными снимками.
- В мастер-плане фиксировать факт, проверку и оставшуюся работу.
- Не менять код ради соответствия устаревшему тексту; сначала сверить
  решение владельца и текущую реализацию.

Для Markdown достаточно `php tests/docs_quality_smoke.php`, проверки
путей/ссылок/примеров. Для кода — подходящие изолированные тесты и
`composer check`; frontend — node --check и npm run build.

Тесты не подключают рабочий bootstrap/.env. SQLite и безопасные драйверы
подготавливаются до запуска; Linux-процессы и systemd проверяются в Linux.
Docker — только локальная отладка, не пересобирать его без необходимости.
`health`, `doctor`, миграции и worker используют сервисы установки и не
являются заменой изолированному тестированию.

Изменения существующих файлов другого агента сохранять. Не создавать
коммит, если его не просили; при коммите код, документация и актуальные
отметки плана должны соответствовать друг другу.
