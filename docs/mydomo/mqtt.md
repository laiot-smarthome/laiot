# MQTT

MQTT — встроенный модуль ядра `modules/core/mqtt`. Его нельзя удалить или
установить отдельно, но можно выключить на `/admin/modules`: строка реестра
получает `enabled=0`, маршруты, меню, helpers и worker перестают работать до
обратного включения. Данные топиков и настроек при выключении сохраняются.

Модуль повторяет пользовательскую модель alpha: дерево топиков, привязка
топика к объекту/свойству/методу, отдельный путь для команды, QoS/retain,
замены значений, «только новые значения» и журнал сообщений. Реализация
новая: SDK-модуль, `ModuleDb`, асинхронный конвейер свойств и Yoyo для
интерфейса.

## Быстрый путь

Цикл приёма и отправки — один процесс с одним долгоживущим соединением:

1. `worker mqtt` держит задачу `serve`; это дочерний процесс worker-а,
   ограниченный `timeout` из манифеста. Перед завершением цикл закрывает
   соединение, worker запускает задачу снова — «вечного» процесса с растущей
   памятью нет. Клиент — `php-mqtt/client` `^2.3` (зависимость composer);
   MQTT 5 и своя реализация протокола не нужны.
2. Клиент `php-mqtt/client` работает с неблокирующим сокетом. `loopOnce`
   читает доступные пакеты и сразу возвращается, поэтому между пакетами
   разбирается очередь команд `module.mqtt`. Рукопожатие ограничено
   таймаутом: брокер, который принял TCP и молчит, даёт ошибку через
   несколько секунд, а не вечный цикл `fread` на 100% CPU.
3. Привязки топиков живут в памяти процесса (`BindingIndex`). Версия снимка
   лежит в CacheStore и увеличивается при сохранении/удалении топика, а
   полный сброс раз в 30 секунд ловит правки другого процесса. На каждое
   входящее сообщение SQL за привязками не выполняется.
4. У привязанного топика значение пишется через `PropertyValueService`.
   Core-конвейер свойства сам выполняет OnChange, историю и доставку
   другим модулям; MQTT-цикл этого не ждёт.
5. Журнал MQTT буферизуется и вставляется пачкой, а не отдельным `INSERT`
   на каждое сообщение. Неизвестный топик регистрируется не чаще
   `unlinked_interval` секунд (по умолчанию раз в час), чтобы шторм датчиков
   не превращался в шторм вставок.
6. Изменение свойства приходит в очередь `module.mqtt`. Процесс приёма
   забирает её между пакетами и отправляет команду через то же соединение.
   Отдельный `core-worker module.mqtt` тоже работает: он обслуживает очередь
   своей ленивой сессией издателя, если процесс приёма не запущен.
7. Собственное эхо входящего значения не публикуется обратно: запись из MQTT
   идёт с источником `mqtt`, и подписчик свойства такие изменения пропускает.

Это не гарантия end-to-end latency: её определяют брокер, БД, очередь
событий и загрузка сервера. Замеры цикла и очередей видны на странице
модуля; отдельного нагрузочного теста с реальным брокером в репозитории нет.

## Данные

Таблицы модуля создаются при первом обращении (`Schema`), потому что
core-модуль не проходит `module:install`:

| Логическая | Физическая | Что хранит |
| --- | --- | --- |
| `topics` | `module_mqtt_topics` | путь, привязка, путь команды, QoS/retain, замены, флаги, последнее значение |
| `history` | `module_mqtt_history` | входящие и исходящие сообщения, направление, payload, привязка, время |
| `settings` | `module_mqtt_settings` | параметры брокера и поведения |

Настройки MQTT лежат в таблице модуля, а не в `module_registry.settings`:
общий экран настроек SDK закрыт для core-модулей, а выключение core-модуля
хранится отдельной строкой реестра. Схема и приведение типов те же, что у
SDK (`ModuleSettings::cast`), поэтому форма не сохраняет мусор и неизвестные
ключи.

Привязка хранит и имена, и id объекта/свойства. Имена нужны для интерфейса,
id — для подписки и доставки; переименование объекта/свойства не ломает
подписку, но подпись в карточке топика обновится после сохранения привязки.

## Подписки и эхо

При сохранении топика с объектом и свойством модуль сам ставит подписку
через `$context->subscriptions()` и снимает её, когда привязка меняется или
топик удаляется (если на это свойство не подписан другой топик). Прямых
записей в `property_subscriptions` нет.

Входящее сообщение пишется в свойство с источником `mqtt`. Изменение
свойства доставляется модулю в `module.mqtt`, но подписчик видит источник
`mqtt` и не отправляет команду обратно. Это защищает от петли
«брокер → свойство → брокер».

## Интеграции на общем соединении

Модуль-интеграция не открывает второй клиент: он регистрирует владельца топика
в реестре `MajorDoMo\Mqtt\Integrations` при своём boot.

```php
use MajorDoMo\Mqtt\Integration;
use MajorDoMo\Mqtt\Integrations;

final class Bridge implements Integration
{
    public function id(): string { return 'example'; }
    public function topics(): array { return ['example/zigbee2mqtt/#']; }
    public function owns(string $topic): bool { return str_starts_with($topic, 'example/zigbee2mqtt/'); }
    public function enqueue(string $topic, string $payload): void
    {
        // Быстро и долговечно: цикл приёма не ждёт разбора сообщения.
        $this->queue->push('module.example', 'example.message', compact('topic', 'payload'));
    }
}

$integrations->addLazy('example', static fn (): Bridge => $container->make(Bridge::class));
```

Цикл подписывается на настройки MQTT плюс `topics()` всех интеграций и отдаёт
каждое сообщение владельцу до разбора привязок `stripmode`. «Ничей» топик
обрабатывает сам MQTT, поэтому чужие пакеты не попадают в дерево топиков.
Ответственность за очередь и worker несёт интеграция: реестр не хранит
сообщения и не повторяет их. Регистрация ленивая — сервисы интеграции могут
зависеть от `ModuleManager`, который в момент boot ещё собирается.

Пример — Zigbee: `Module::boot` регистрирует интеграцию, MQTT-цикл ставит
задание `zigbee.message` в `module.zigbee`, а `worker zigbee` или
`core-worker module.zigbee` разбирает пакет. Устройство —
[zigbee.md](zigbee.md).

## Настройки

| Ключ | Смысл |
| --- | --- |
| `host`, `port` | адрес брокера |
| `client_id` | префикс client id; PID и случайный хвост добавляются автоматически |
| `auth`, `username`, `password` | авторизация |
| `tls`, `tls_ca`, `tls_verify` | TLS и проверка сертификата |
| `query` | список фильтров через запятую или с новой строки |
| `keepalive` | интервал ping, секунды |
| `stripmode` | не обрабатывать топики без привязки и без привязанных дочерних путей |
| `unlinked_interval` | как часто обновлять значение топика без привязки; `0` — каждое сообщение |
| `dedup_seconds` | подавление одинакового payload топика в течение интервала |
| `history_keep_days` | срок хранения журнала; чистится задачей `maintenance` |
| `debug` | писать входящие/исходящие в общий журнал |

Сохранение увеличивает версию в CacheStore; цикл замечает её в течение
нескольких секунд и переподключается. После выключения модуль проверяет
реестр и завершает задачу в пределах того же окна.

## Интерфейс

- `/module/mqtt` — список топиков и состояние цикла. Поиск, группы
  «устройства/пути», фильтры, сортировка, страницы и автообновление значений
  сделаны Yoyo-компонентами `mqtt-topics` и `mqtt-status`. Отдельного
  JSON-эндпоинта для списка нет; автообновление — `Yoyo.dispatch('mqtt-refresh')`,
  пока фокус не в поле компонента.
- `/module/mqtt/topics/create`, `/module/mqtt/topics/<id>/edit` — карточка
  топика: путь, команда, объект/свойство/метод (`x-md.linked-object`),
  QoS/retain, замены, журнал, дочерние топики и ручная отправка.
- `/module/mqtt/settings` — брокер, авторизация, TLS, поведение; проверка
  соединения по сохранённым значениям.

Изменяющие действия — обычные POST-маршруты с CSRF; Yoyo отвечает только за
состояние интерфейса. Страницы и Yoyo-компоненты требуют права
`settings.manage` (у администратора оно есть по `*`), поэтому список топиков
не открывается обычному пользователю даже прямым запросом `/yoyo`.

## Фоновые процессы

```bash
php bin/mydomo worker mqtt          # приём и отправка
php bin/mydomo worker mqtt --once   # ограниченный проход для диагностики
```

`serve` — длинная задача: на Linux она выполняется в дочернем процессе
worker-а, а `--once` ограничивает её двумя секундами. `maintenance` чистит
журнал по сроку. Без worker-а значения не обновляются, а команды копятся в
`module.mqtt`; страница модуля показывает это как «worker не запущен».

Для systemd используется `deploy/systemd/mydomo-worker@.service`
(`mydomo-worker@mqtt`). Выключение модуля в панели не останавливает уже
запущенный процесс мгновенно: цикл завершится сам после проверки реестра,
а unit при желании можно остановить отдельно.

## Helpers

```php
mqtt_publish('home/living/set', '1', qos: 1, retain: true);
mqtt_value('home/living/state');
mqtt_connected();
```

`mqtt_publish` возвращает `false` при ошибке брокера и пишет причину в
RuntimeState; исключение в сценарий не летит. Функции доступны, пока модуль
включён.

## Ограничения

- MQTT 3.1 и 3.1.1; MQTT 5 не используется.
- Один процесс приёма: параллелизм есть у событий свойства, но разбор
  входящего потока одного брокера последовательный.
- Импорта данных alpha `mqtt`/`mqtt_history` нет; сторонние модули
  подключаются к сообщениям через `Integrations` (см. выше), а не общим
  брокером внутри процесса.
- Переименование объекта/свойства не ломает запись по id, но подпись в
  карточке топика и вызов привязанного метода используют сохранённое имя:
  после переименования объекта или метода откройте топик и сохраните
  привязку заново. Ядро не переписывает таблицы модуля.
- HTTP-публикация из alpha (`PATH_WRITE` вида `http://…`) не перенесена.
- История хранится по сроку, а не «последние N записей на топик»; ручная
  оптимизация в alpha заменена очисткой по `history_keep_days`.
- Проверка соединения в форме открывает отдельное соединение и не
  подменяет работающий цикл; при ошибке она показывает текст ошибки, а не
  перезапускает worker.

Проверки: `tests/Feature/MqttModuleTest.php` — страницы, Yoyo-обновление,
настройки, приём, отправка и lifecycle core-модуля (SQLite, без брокера).
Живой брокер проверяется вручную на стенде.
