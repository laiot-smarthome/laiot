# Очередь и таймеры

`DatabaseQueue` хранит именованные задания в БД. Это отдельный механизм
от задач SDK-модуля и от строк PHP в `runtime_timeouts`. Redis используется
для состояния фоновых процессов, но не хранит payload очереди.

## Создание и обработчик

```php
$app->jobs()->register('demo.record', static function (array $payload): void {
    // Один законченный шаг: данные доступны в $payload.
});
$id = $app->queue()->push('default', 'demo.record', ['value' => 42], 10);
```

`push($queue, $job, $payload = [], $delaySeconds = 0): int` возвращает ID.
Payload кодируется как JSON; обработчик должен принимать массив. Объект,
реализующий `Job`, предоставляет `name(): string` и `payload(): array`:
`pushJob($job, $queue = 'default', $delaySeconds = 0)` создаёт такое же
задание. Код обработчика в таблицу не записывается.

Регистрация `JobRegistry::register()` действует в текущем процессе.
В другом CLI-процессе обработчик должен быть зарегистрирован его boot-
кодом; регистрация в одном HTTP-запросе не появляется автоматически у
worker. Неизвестное имя задания завершается ошибкой и идёт в retry.

## Жизненный цикл

1. `push` задаёт `available_at`; до этого момента задание не выдаётся.
2. `pop` выбирает готовое задание и условным UPDATE ставит `reserved_at`.
3. `QueueWorker::work()` запускает обработчик.
4. `ack` физически удаляет успешно обработанную строку.
5. `fail` увеличивает `attempts`, сохраняет ошибку, снимает резервацию.
6. До лимита попыток назначается новое `available_at`; на лимите
   заполняется `failed_at`, и задание больше не выдаётся.

Параметры `config/queue.php`:

| Ключ | Значение | Смысл |
| --- | --- | --- |
| `table` | `queue_jobs` | Общая таблица заданий |
| `max_attempts` | `3` | Лимит обработанных ошибок до failed |
| `retry_delay` | `60` | Задержка после ошибки, секунды |
| `reservation_timeout` | `300` | Когда можно забрать просроченную резервацию |
| `events_lanes` | `4` | Число полос очереди событий; одна полоса свойства |

После падения процесса задание снова доступно по истечении резервации.
Это не гарантия единственного исполнения: обработчик должен переносить
повтор после частично выполненного действия. Срок резервации должен
соответствовать длительности работы; у `QueueWorker` нет собственного
таймаута пользовательского обработчика.

`attempts` увеличивается при `fail`, а не просто при `pop`. Аварийное
завершение процесса не равнозначно зафиксированной ошибке обработчика.
Каждая резервация получает токен: запоздавший `ack/fail` старого воркера
не меняет задание, уже переданное другому воркеру. Перед обновлением кода
необходимо применить миграцию столбца `reservation_token`; для собственного
имени таблицы очереди столбец нужно подготовить в этой таблице отдельно.

## Просмотр и повтор

```php
$app->queue()->stats('default');       // pending, reserved, failed
$app->queue()->pending('default', 50);
$app->queue()->failed('default', 50);
$app->queue()->retry($id);
$app->queue()->forget($id);
```

`pending`/счётчик pending учитывают уже готовые задания, включая просроченные
резервации; будущие отложенные задания в этот счётчик не входят.
`retry` работает с failed-строкой: сбрасывает attempts/error и делает её
доступной сейчас. `forget` физически удаляет failed-строку.
В панели те же операции находятся в `/jobs` и защищены сессией и CSRF.

## Два режима запуска

```bash
php bin/mydomo queue:stats --queue=default --json
php bin/mydomo queue:failed --queue=default --limit=50 --json
php bin/mydomo queue:work --queue=default --once
php bin/mydomo queue:work --queue=default --max-jobs=100
php bin/mydomo core-worker queue
```

`queue:work` обрабатывает доступные задания и заканчивается, когда очередь
пуста; без `--max-jobs` он не становится постоянным daemon. `--once` — не
более одного задания. Этот CLI возвращает успех после обработанного
прохода, даже если обработчик записал задание в failed/retry: проверяйте
журнал и статистику, а не только exit code.

`core-worker queue` — постоянный процесс с ожиданием, сигналами и состоянием
`BackgroundTaskState`; сейчас он работает с очередью `default`.
`core-worker events` так же обслуживает очередь событий свойства. `worker
<module>` запускает задачи из `module.json` и не заменяет ни одну из этих
команд. Systemd и Redis — в [runtime.md](runtime.md).

## Очередь `events`

Запись свойства кладёт задание `property.changed`; обработчик выполняет
OnChange, историю и доставку модулям. Это единственная очередь, где важен
порядок: цепочка `A → B → A` и гашение эха полагаются на то, что события
одного свойства обрабатываются по одному.

События разложены по полосам: номер полосы считается от объекта и свойства,
поэтому все изменения одного свойства всегда попадают в одну очередь.
Полос `queue.events_lanes` (по умолчанию 4), имена — `events.0`…`events.3`;
при одной полосе имя остаётся `events`.

```bash
php bin/mydomo core-worker events            # все полосы, один процесс
php bin/mydomo core-worker events.2          # только полоса 2
```

Для параллельной работы запускается по процессу на полосу через
`mydomo-core@events.0`…`mydomo-core@events.3`. Один `core-worker events`
тоже корректен — он обходит полосы по кругу, но обрабатывает их
последовательно. Нельзя одновременно запускать «все полосы» и отдельные
полосы: одна полоса должна обслуживаться одним процессом.

- Полоса выбирается стабильной функцией `crc32(объект:свойство)`, поэтому
  после рестарта событие попадает туда же.
- Число полос меняется только остановкой очереди: задания старых имён
  `events.<n>` не переедут сами.
- Задание несёт цепочку и родителя журнала, поэтому повтор после падения не
  теряет контекст, но может повторить пользовательский код: он должен быть
  идемпотентным, как любой обработчик очереди.
- Failed-задания: `queue:failed --queue=events.0`, повтор — `queue:retry`.

## Очереди модулей

У каждого модуля своя очередь `module.<id>`: изменения свойств, на которые он
подписан. Её обслуживает `worker <id>` — тот же процесс, что выполняет задачи
модуля. Поэтому медленный подписчик задерживает только свой модуль, а не
events и не другие модули.

```bash
php bin/mydomo queue:stats --queue=module.mqtt
php bin/mydomo worker mqtt --once       # задачи модуля и накопленная доставка
```

`worker --once` выполняет задачи и опустошает доступную очередь доставки;
постоянный worker ждёт новые задания вместе с задачами по интервалам.
Неизвестный модуль или выключенный модуль очередь не обслуживает: задания
остаются до включения worker'а.

## setTimeOut

`setTimeOut($title, $code, $seconds, $expire = 0)` записывает PHP-код в
`runtime_timeouts`; `$expire` текущей обёрткой не используется. Одинаковое
имя не заменяет существующую запись автоматически. `clearTimeOut($title)`
снимает все ещё не выполненные записи с этим именем.

`timeout:run` делает один проход; `core-worker timeouts` — постоянный
процесс. Запись забирается с арендой (`claimed_at`, `claim_token`): второй
процесс не выполнит её одновременно, а подтверждение и снятие привязаны к
токену. Успех помечается `executed_at`; ошибка снимает аренду и возвращает
код в следующий проход. Просроченная аренда (300 секунд) снова доступна,
поэтому падение процесса не «замораживает» таймер. Политики failed/retry,
аналогичной `queue_jobs`, у таймеров по-прежнему нет: после ошибки запись
повторяется без счётчика попыток.

Миграции применяются через `db:migrate`. Некоторые низкоуровневые сервисы
могут создавать свои таблицы при обращении, но это не замена подготовке
схемы. Команды в этом документе меняют БД или выполняют код; они не являются
проверками, которые следует безусловно запускать на рабочей установке.
