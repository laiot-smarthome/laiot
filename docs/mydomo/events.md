# Цепочка событий свойства

В MyDoMo изменение свойства — это не просто `UPDATE` значения. Запись
сохраняет значение и в той же транзакции ставит задание `property.changed`
в очередь `events`. Всё остальное — журнал, OnChange-метод, история и
доставка модулям — выполняет отдельный процесс `core-worker events`.

Почему так: в секунду могут меняться тысячи свойств, у каждого своя цепочка,
свой пользовательский код и свои привязки. Синхронный запуск всех методов в
запросе датчика превратил бы приём данных в очередь ожидания. Запись теперь
не зависит от пользовательского PHP, а события обрабатываются в своём
процессе, не деля его с модульными задачами.

Внутри обработчика порядок такой: OnChange-метод → история → доставка
модулям. Реакция на изменение не ждёт учёта и уведомлений.

## 1. Один путь записи

| Откуда пишут | Что вызывается |
| --- | --- |
| Сценарий или метод: `sg('Кухня.temperature', 23.5)` | `PropertyValueService::set()` |
| Вкладка «Свойства и значения» объекта (`/objects/<id>/values`) | `PropertyValueService::setValue()` |

`ValueRepository::write()` — низкоуровневая запись без истории и цепочки: она
нужна импорту и точечным тестам, а не пользовательскому коду. `sg()` обходит
только её и всегда идёт через сервис.

Свойство ищется сначала среди объектных свойств объекта, затем в его классе
и по цепочке наследования. Одноимённое объектное свойство перекрывает
классовое у этого объекта; ближайший подкласс перекрывает родительский
класс. Глобального свойства (`class_id = 0`) вне объекта нет: значение
всегда принадлежит конкретному объекту.

`PropertyValueService::setValue($objectId, $propertyId, $value, $source = 'panel')`
возвращает `false`, если объект/свойство удалены, свойство принадлежит
другому объекту или перекрыто более близким членом с тем же названием.
Отказ не меняет значения, историю и журнал событий. Обновление и
восстановление значения сохраняют его первоначальный `created_at`;
меняется только `updated_at`.

## 2. Что происходит при записи

1. Значение приводится к строке: `null` → `''`, `false` → `'0'`,
   `true` → `'1'`, массив → JSON.
2. Читается старое значение; вычисляется, изменилось ли оно.
3. Значение сохраняется в `property_values`, и в той же транзакции в
   `queue_jobs` кладётся задание `property.changed` для очереди `events`.
   На этом запрос свободен.
4. `core-worker events` берёт задание и создаёт в `property_events` якорь
   `property.changed`. Он нужен вложенным записям как родитель и остаётся
   видимым, если обработчик завис.
5. Если у свойства задан `on_change` — сразу вызывается одноимённый метод
   класса объекта с параметрами `OBJECT`, `PROPERTY`, `OLD_VALUE`,
   `NEW_VALUE`, `SOURCE`, `DEPTH`, `CHAIN`. Реакция не ждёт историю и
   доставку.
6. После метода пишется история (если включён `keep_history` и значение
   изменилось). Время строки — время записи значения, а не возврата метода.
7. Затем каждому подписанному модулю ставится задание в его очередь
   `module.<id>`; worker модуля создаёт шаг `module.delivery` и вызывает
   обработчик. Модули не выполняются в процессе events.
8. Вложенная запись внутри метода или подписчика — это новое задание с
   цепочкой и родителем из текущего контекста.

Повторная запись того же значения не создаёт вторую строку истории и не
создаёт `property.changed`, но подписчики и OnChange-метод всё равно
вызываются: нажатие кнопки или повторная команда — это событие, даже если
состояние не изменилось. У такого вызова `PropertyChange::$changed = false`.

`sg()` возвращает `true` после сохранения значения и постановки задания, а не
после выполнения метода. История и журнал появляются, когда задание
обработано; при остановленном `core-worker events` они отстают, а значения
продолжают сохраняться. Задание durable: после падения процесса оно снова
доступно по правилам очереди.

## 3. Журнал `property_events`

Таблица — только журнал: строки создаёт сервис, пользовательский код в неё не
пишет. Поля:

| Поле | Смысл |
| --- | --- |
| `parent_id` | шаг, из которого появился этот; `0` — корень цепочки |
| `type` | `property.changed`, `handler.method` или `module.delivery` |
| `status` | `changed`, `stopped`, `running`, `ok`, `error`, `missing`, `skipped` |
| `source` | кто записал: `sg`, `panel:pvalues`, `panel:objects` или id модуля |
| `object_id`, `property_id`, `object_title`, `property_title` | что изменилось |
| `old_value`, `new_value` | значения до и после |
| `handler` | имя OnChange-метода или id модуля-подписчика |
| `message` | причина остановки или текст ошибки |
| `chain` | JSON-цепочка вида `["Кухня.alarm","Кухня.temperature"]` |
| `depth` | номер шага: запись — 0, её обработчик — 1, вложенная запись — 1 и т.д. |

Строка обработчика создаётся со статусом `running` до запуска пользовательского
кода и финализируется после. Поэтому «зависший» обработчик виден в журнале, а
вложенные записи сразу получают правильного родителя.

Страница журнала — `/events` (core-модуль `events`): поиск по объекту,
свойству, обработчику и значению, фильтры по типу и статусу.

## 4. Доставка модулям

Подписку выбирает **пользователь**, а не модуль: в интерфейсе модуля он
указывает, какие объекты и свойства этот модуль обслуживает. Манифест
объявляет только класс-обработчик (`property_subscriber`), потому что в
разных установках один и тот же модуль подключён к разным устройствам.

Подписка хранится в `property_subscriptions` строкой «объект + свойство +
модуль» (`PropertySubscriptionRepository`). Отдельная таблица вместо колонки
`pvalues.LINKED_MODULES` alpha: нет ограничения `varchar(255)` и гонки
«прочитать-переписать» при параллельной правке.

Модуль получает `PropertyChange` (`objectTitle`, `propertyTitle`, `oldValue`,
`newValue`, `source`, `changed`, `chain`, `depth`) в **своём** процессе:
events-обработчик не вызывает код модуля, а кладёт задание в очередь
`module.<id>`, которую обслуживает `worker <id>`. Медленный модуль
задерживает только свою очередь; события свойств и другие модули идут дальше.

Ошибка обработчика не откатывает значение: строка `module.delivery` получает
статус `error` с текстом исключения, и это не мешает другим модулям. Если
модуль не зарегистрировал обработчик — статус `missing`.

Модуль не получает эхо собственной записи: пока он обрабатывает изменение,
его собственные записи не возвращаются ему как новое событие. Другие
подписчики и OnChange получают их как обычно. Отдельного параметра для этого
нет — контекст ведёт сервис записи, а не вызывающий код.

Повторная запись того же свойства внутри обработчика останавливается
цепочкой: это защита от цикла, а не от эха. Пример: `onChange` датчика пишет
команду лампе. `Кухня.temperature` и `Лампа.state` — разные токены, поэтому
команда уходит подписчику, а возврат к `Кухня.temperature` — нет.

## 5. Защита от циклов

Если обработчик снова приходит к свойству, которое уже есть в цепочке
(`A → метод → B → метод → A`), значение сохраняется, но следующий обработчик не
вызывается. Шаг получает статус `stopped`, в `message` пишется причина. Тот же
предел — 32 шага (`PropertyEventContext::MAX_DEPTH`).

Это важное отличие от «молчаливого» обрыва: данные датчика не теряются, а
остановка видна в журнале и на странице событий.

## 6. Ошибки обработчика

Код метода — доверенный пользовательский PHP. Его исключение не откатывает
значение: запись уже состоялась, а шаг обработчика получает статус `error` с
текстом исключения и предупреждение уходит в лог приложения. Если метода нет —
статус `missing`.

Так автоматизация не превращает ошибку в потере данных: значение сохранено,
история и журнал заполнены, ошибка видна в `/events`.

## 7. Чего пока нет

- динамического изменения числа полос: `queue.events_lanes` фиксируется при
  запуске, а задания старых имён `events.<n>` сами не переезжают;
- автоматического масштабирования: процессы `events.<n>` запускаются
  администратором, ядро не поднимает их само;
- привязки сценариев к свойству (только OnChange-метод класса);
- retention журнала: строки не удаляются автоматически;
- отдельного API-события: журнал доступен только странице админки;
- выбора подписок в интерфейсе модуля: сервис подписок готов, страницы модулей
  появятся вместе с переносом MQTT/Zigbee.

Пока контракт такой: значение сохраняется всегда, остановка видна в журнале,
ошибка подписчика или метода не откатывает данные.

## 8. Пример

Свойство `Кухня.temperature` класса «Датчик», `keep_history = 1`,
`on_change = onTemperature`:

```php
// метод onTemperature того же класса
if (($params['NEW_VALUE'] ?? '') === 'hot') {
    sg('Кухня.alarm', '1');
}

return true;
```

```php
sg('Кухня.temperature', 'hot');
```

В журнале появятся шаги:

```text
0  property.changed  Кухня.temperature  '' → hot     changed
1  handler.method    onTemperature                   ok
1  property.changed  Кухня.alarm        '' → 1       changed
2  handler.method    onAlarm                         ok
...
```

Если `onAlarm` снова запишет `Кухня.temperature`, шаг остановится со статусом
`stopped`.

Если на `Кухня.temperature` подписан модуль, его шаг появится после метода и
будет создан уже worker'ом модуля:

```text
0  property.changed  Кухня.temperature  '' → hot     changed
1  handler.method    onTemperature                   ok
1  module.delivery   mqtt                            ok
```

## 9. Проверка

```bash
php vendor/phpunit/phpunit/phpunit --filter CoreEventsTest
php vendor/phpunit/phpunit/phpunit --filter PropertyDeliveryTest
```

Тесты Feature после `sg()` явно прогоняют очереди: `DrainsEvents::drainEvents()`
выполняет `property.changed` и затем очереди `module.<id>` до пуста. Без этого
журнал, история и вызовы модулей ещё не выполнены — запись асинхронна.

Первый тест поднимает SQLite в памяти, создаёт класс, объект, свойства и методы
и проверяет изменение значения, повторную запись, цикл, ошибку обработчика,
отсутствующий метод, разрешение свойства по классу и запись со страницы
значений. Второй — подписку, доставку, гашение эха, ошибку подписчика,
остановку цикла и идемпотентность подписки.
