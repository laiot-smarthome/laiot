# Журналы и диагностика

У нового ядра несколько разных журналов. Запись в один из них не означает,
что то же событие обязательно появится во всех остальных.

| Источник | Где смотреть | Назначение |
| --- | --- | --- |
| Monolog | `var/log/<channel>.log` | Поток по каналам с суточной ротацией |
| Отдельный файл ошибки | `var/log/errors/<дата>-<id>-<hash>.log` | Контекст и trace одной записи `system_errors`; открывается из `/errors` |
| `system_errors` | `/errors` | Ошибки, зарегистрированные ErrorRepository |
| `action_log` | `/journal` | Вход/выход и явно добавленные действия пользователей |
| `property_events` | `/events` | Запись свойства и выполнение OnChange |
| `queue_jobs` | `/jobs`, `queue:failed` | Ожидание, резервация и ошибки заданий |
| `notifications` | `/notifications`, колокольчик | Сообщения, требующие внимания/прочтения |
| Состояние worker | CacheStore, `BackgroundTaskState` | Текущий lock, heartbeat и следующее выполнение |

## Связать ответ и ошибку

`Kernel` принимает `X-Request-Id`, если он состоит из 1–64 символов
`[A-Za-z0-9._-]`, иначе создаёт свой. ID добавляется в заголовок ответа,
request attributes и `RequestContext`. Процессор Monolog помещает его
в `extra.request_id`; при необработанной HTTP-ошибке он также передаётся
в ErrorRepository.

При обращении с проблемой достаточно пути запроса, времени и request ID.
Пароль, Cookie, Bearer и секрет webhook в диагностический отчёт не нужны.
Не все контроллеры используют единый JSON-конверт: ID в заголовке надёжнее
ожидания поля в каждом JSON-теле.

## Каналы и уровень

`LoggerFactory` создаёт именованные Monolog-каналы: `app`, `http`, `security`,
`queue`, `events`. В production каждый канал пишет в свой файл
`var/log/<channel>.log`; `RotatingFileHandler` хранит `logging.max_files`
последних дней (по умолчанию 14). Поток `log=php://stderr` (тесты, CLI с
явной настройкой) оставляет один вывод, но имя канала остаётся в записи.

Уровень: `debug=true` включает Debug, иначе берётся `logging.level`
(`info` по умолчанию). `config/logging.php` используется сборкой логгера:
`directory`, `max_files`, `level`, `error_directory`.

## Файл на каждую ошибку

Каждая запись `system_errors` получает собственный файл в
`var/log/errors/`: ID, уровень, request ID, путь, сообщение, класс,
`file:line` и stack trace. Имя файла генерирует ядро, снаружи путь не
принимается. Путь хранится в `system_errors.log_file`; удаление записи или
группы в `/errors` удаляет и файл.

В режиме «Все записи» `/errors` у записи с файлом есть ссылка «Открыть файл
ошибки» (`/errors/<id>/file`). Страница читает только файл внутри
`var/log/errors`: значение `log_file` с `..`, абсолютным путём или чужим
каталогом отклоняется, отсутствующий файл даёт 404. Большой файл
показывается первыми 512 КБ с предупреждением; полный файл остаётся на
сервере.

Страница `/errors` — Yoyo-экран из двух полноширинных режимов. Сначала список:
фильтры, группы повторяющихся сообщений или все записи. По нажатию
открывается отдельный экран деталей: время, уровень, класс исключения,
`file:line`, путь, request ID, число и период повторов, стек по кадрам,
контекст и исходный файл. Кнопка «Скопировать для AI» кладёт в буфер
готовый текстовый отчёт с сообщением, местом, повторами, контекстом и стеком.
Возврат — «К списку ошибок», без потери фильтров. Отдельная страница файла
`/errors/<id>/file` осталась для прямой ссылки и полного raw-текста.

Это относится к ошибкам, зарегистрированным `ErrorRepository` (например,
необработанная ошибка HTTP-запроса). Обычная строка Monolog отдельного файла
не получает — она идёт в поток канала.

## Что проверять последовательно

1. Проверить HTTP-статус и request ID. Для API использовать
   `Accept: application/json`.
2. Для 401/403 проверить способ входа, CSRF и явно заданный `can:`:
   [authentication.md](authentication.md).
3. Для значения без ожидаемого действия смотреть `/events`, его статус
   `missing/error/stopped/skipped`, а не только историю значений.
4. Для задания смотреть `queue:stats` и `queue:failed`; успешный выход
   процесса не всегда означает успех каждого обработчика.
5. Для фонового модуля отдельно проверять его worker и Redis-состояние.
   Доступная панель не доказывает, что запущены все фоновые процессы.

`/health` проверяет только основную БД и roundtrip кэша. `doctor` дополняет
это расширениями PHP и доступностью runtime-каталогов. Ни одна из этих
проверок не является полной проверкой MQTT, системного агента, всех задач
или выполнения пользовательских автоматизаций.

## Retention

Сроки хранения задаёт `config/retention.php`: `history_days`, `events_days`,
`queue_days`, `timeouts_days`, `errors_days`, `batch` и `interval`. `0`
отключает очистку раздела. Очистка выполняется порциями, чтобы не блокировать
запись значений.

- `db:prune` — ручной прогон; `--dry-run` только считает строки.
- `core-worker maintenance` — постоянный процесс: очистка сразу и затем раз в
  `retention.interval` секунд (по умолчанию 6 часов). В systemd это
  `mydomo-core@maintenance`.

Удаляются только устаревшие данные: история и журнал свойств, окончательно
упавшие задания (`failed_at`), выполненные или отменённые таймеры и старые
`system_errors` вместе с их файлами. Ожидающие задания и ещё не выполненные
таймеры остаются. Retention удаляет строки физически, а не через soft delete:
цель — вернуть место. Ошибка очистки пишется в канал `queue` и не роняет
процесс.
