# Журналы и диагностика

У нового ядра несколько разных журналов. Запись в один из них не означает,
что то же событие обязательно появится во всех остальных.

| Источник | Где смотреть | Назначение |
| --- | --- | --- |
| Monolog | `var/log/mydomo.log` по умолчанию | Инфраструктурные ошибки, worker, контекст запросов |
| `system_errors` | `/errors` | Ошибки, зарегистрированные ErrorRepository |
| `action_log` | `/journal` | Вход/выход и явно добавленные действия пользователей |
| `property_events` | `/events` | Запись свойства и выполнение OnChange |
| `queue_jobs` | `/jobs`, `queue:failed` | Ожидание, резервация и ошибки заданий |
| `notifications` | `/notifications`, колокольчик | Сообщения, требующие внимания/прочтения |
| Состояние worker | CacheStore, `BackgroundTaskState` | Текущий lock, heartbeat и следующее выполнение |

## Связать ответ и ошибку

`Kernel` принимает `X-Request-Id`, если он состоит из 1–64 символов
`[A-Za-z0-9._-]`, иначе создаёт свой. ID добавляется в заголовок ответа,
request attributes и `RequestContext`. Процессор Monolog помещает его
в `extra.request_id`; при необработанной HTTP-ошибке он также передаётся
в ErrorRepository.

При обращении с проблемой достаточно пути запроса, времени и request ID.
Пароль, Cookie, Bearer и секрет webhook в диагностический отчёт не нужны.
Не все контроллеры используют единый JSON-конверт: ID в заголовке надёжнее
ожидания поля в каждом JSON-теле.

## Каналы и уровень

`LoggerFactory::channel('app'|'http'|'security')` создаёт именованные
Monolog-каналы. Сейчас они используют один StreamHandler и общий путь.
При `debug=false` уровень Info, при `true` — Debug. Отдельной настроенной
ротации или файлов по каналам пока нет.

Секция `config/logging.php` загружается ConfigLoader, но фактическая сборка
логгера пока получает `Application`-ключи `log` и `debug`. Подробности
этого ограничения — в [configuration.md](configuration.md).
Отключённый HTTP-debug скрывает подробности от клиента, а не удаляет
исключение из серверного журнала.

## Что проверять последовательно

1. Проверить HTTP-статус и request ID. Для API использовать
   `Accept: application/json`.
2. Для 401/403 проверить способ входа, CSRF и явно заданный `can:`:
   [authentication.md](authentication.md).
3. Для значения без ожидаемого действия смотреть `/events`, его статус
   `missing/error/stopped/skipped`, а не только историю значений.
4. Для задания смотреть `queue:stats` и `queue:failed`; успешный выход
   процесса не всегда означает успех каждого обработчика.
5. Для фонового модуля отдельно проверять его worker и Redis-состояние.
   Доступная панель не доказывает, что запущены все фоновые процессы.

`/health` проверяет только основную БД и roundtrip кэша. `doctor` дополняет
это расширениями PHP и доступностью runtime-каталогов. Ни одна из этих
проверок не является полной проверкой MQTT, системного агента, всех задач
или выполнения пользовательских автоматизаций.

Retention для системных ошибок, цепочек и уведомлений нельзя выводить
из наличия похожих alpha-настроек: автоматическое обслуживание этих
таблиц нужно подтверждать конкретным кодом нового ядра.
