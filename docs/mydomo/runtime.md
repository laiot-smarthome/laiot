# Фоновый runtime

В приложении три разных вида фоновой работы: задачи SDK-модуля, очередь
именованных заданий и пользовательские таймеры. Они не запускаются из
HTTP автоматически. Linux/systemd — рабочая платформа; Windows подходит
для доступных тестов, но не доказывает корректность fork и Unix-сокетов.

## Worker SDK-модуля

Манифест объявляет tasks, entrypoint предоставляет публичный метод:

```json
{
  "tasks": {
    "poll": {"method": "poll", "interval": 60, "timeout": 30, "enabled": true}
  }
}
```

```php
public function poll(\MajorDoMo\Worker\BackgroundTaskContext $context): void
{
    // Один проход. Планирование и повторный вызов принадлежат worker.
}
```

Команды: `worker <id>` — постоянный процесс; `worker <id> --once` —
один проход включённых задач. Нужен подключённый модуль с entrypoint и
вызываемым методом. Модуль без включённых tasks заканчивает работу без
создания полезной фоновой нагрузки.

Один worker обслуживает задачи модуля последовательно. Манифест разрешает
interval 1–86400 секунд и timeout 1–3600 секунд, значения по умолчанию 60.
По сигналам SIGTERM/SIGINT выставляется флаг остановки; ошибка задачи
пишется в журнал и состояние, а не обязательно завершает весь worker
ошибочным кодом. Проход --once не является sandbox или симуляцией.

При доступных pcntl_fork/pcntl_waitpid задача выполняется в дочернем
процессе. Родитель ждёт, контролирует deadline и завершает просроченного
ребёнка через posix_kill. Нужны проверенные pcntl/posix в Linux.
Без pcntl код исполняется в текущем процессе без принудительного timeout.
Состояние PHP-объекта, изменённое ребёнком, не переносится назад в память
родителя: долговечные результаты сохраняйте через сервисы/хранилище.

## Состояние и lock

BackgroundTaskState использует общий CacheStore:

| Данные | Логическое имя ключа | TTL |
| --- | --- | --- |
| Lock модуля | `worker.lock.<id>` | 120 секунд |
| Lock ядровой задачи | `worker.lock.core.<task>` | 120 секунд |
| Состояние задачи | `worker.task.<id>.<task>` | 86400 секунд |

Физические ключи также имеют префикс CacheStore, обычно `mydomo.`.
Состояние содержит сведения о запуске/завершении, ошибке и следующем
выполнении; это не бесконечный журнал всех запусков.

Для production предполагается Redis. Конструктор не запрещает file/array,
поэтому правильный драйвер должен быть настроен явно. Array не разделяет
lock между процессами. Lock продлевается в точках цикла, а не независимо
во время любого блокирующего обработчика: длительная работа может пережить
его TTL. Очистка прикладного кэша удаляет и эти ключи.

Планирование внутри worker использует также локальное состояние процесса;
наличие next_run в Redis не означает полностью распределённый планировщик
с восстановлением всех интервалов после любого рестарта.

## Процессы ядра

`core-worker queue` постоянно обслуживает очередь default;
`core-worker timeouts` — созревшие записи runtime_timeouts. `--once`
ограничивает их одним шагом/проходом. Разовые `queue:work` и `timeout:run`
не заменяют постоянный сервис. Семантика повторов — [queue.md](queue.md).

Шаблоны: `deploy/systemd/mydomo-worker@.service` и
`deploy/systemd/mydomo-core@.service`. MemoryMax=256M ограничивает сервис;
ядровой шаблон добавляет Nice=-5 и CPUWeight=500. Это задаёт приоритет,
но не гарантирует задержку jobs при общей занятости БД, диска или CPU.
Сами PHP-классы не устанавливают такой предел памяти вместо systemd.

OnChange пока синхронен. Отдельный events/outbox-процесс — план;
`core-worker events` сейчас не поддерживается.

## Административный агент

`bin/mydomo-agent` — отдельный процесс, в шаблоне сервиса работает от root.
Веб-приложение не должно само писать `/etc/systemd/system` или выполнять
произвольный systemctl. Связь — JSON через Unix socket, по умолчанию
`/run/mydomo/agent.sock` с правами 0660.

Настройки берутся из `/etc/mydomo/agent.json`, а не из рабочего `.env`.
`MYDOMO_AGENT_CONFIG` меняет путь к JSON. Пример структуры с условными
значениями, которые администратор заменяет для своей установки:

```json
{
  "root": "/srv/mydomo",
  "user": "mydomo",
  "group": "mydomo",
  "socket": "/run/mydomo/agent.sock",
  "systemctl": "/usr/bin/systemctl",
  "unit_dir": "/etc/systemd/system",
  "allowed_uid": 1000
}
```

Действия протокола:

- `worker.start/stop/restart/status`, поле module с ID модуля.
- `core.start/stop/restart/status`, поле module: queue либо timeouts.
- `workers.sync`, поле modules со списком желаемых модулей.
- `cores.sync`, поле tasks со списком ядровых задач.
- `worker.install` — установка обоих шаблонов через installAllUnits.

```json
{"action": "worker.restart", "module": "weather"}
```

Ответ: `ok` и `data` либо `ok=false/error`. Имена проверяются контроллером,
аргументы systemctl передаются массивом без shell-конкатенации. Доступ к
сокету является административной возможностью и должен быть ограничен
владельцем/группой. allowed_uid проверяется только при наличии
posix_getpeereid; нельзя обещать обязательную проверку peer UID на каждой
Linux-сборке PHP.

## Установка: что существует сейчас

Сервис агента описан в `deploy/systemd/mydomo-agent.service`; пути и
пользователи в шаблонах подставляются из конфигурации SystemdController.
Запуск и установка сервисов — отдельная административная операция,
не побочный эффект открытия панели.

`php bin/mydomo-agent install` сейчас вызывает installUnit и устанавливает
только worker-шаблон. Установка обоих шаблонов реализована методом
installAllUnits и действием протокола worker.install. Готовой единой CLI-
последовательности установки всей системы здесь пока нет. Ранее приведённый
набор команд с install нельзя считать завершённым production-installer.

Проверять владельца сокета, пользователя worker, абсолютный root,
зависимости PHP, Redis и фактическую работу юнитов нужно на Linux.
Docker-стенд без systemd не заменяет эту проверку.

## Обновление остаётся проектом

Принятое направление: пользователь запускает обновление вручную,
доступность версии проверяется отдельно, сборка — на его сервере,
переключение releases/current атомарное, после health — подтверждение или
откат. Установка Composer/npm, миграции и рестарт должны иметь обработку
ошибок и проверенный порядок.

UpdateService, кнопка обновления, автоматизированный откат и supervisor-
адаптер пока не реализованы этим runtime. Старый deploy alpha не является
эквивалентом нового update-процесса. Будущие шаги — в мастер-плане;
не выдавайте их за уже доступные команды.
