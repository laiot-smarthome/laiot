# Вход и права MyDoMo

Три механизма имеют разные назначения: браузерная сессия открывает панель,
`Authorization` проверяет разрешения, API-токен аутентифицирует запрос к
токенному API. Они не подменяют друг друга.

## Вход в панель

| Запрос | Результат |
| --- | --- |
| `GET /` или `GET /login` | Форма входа; при наличии сессии переход на `/admin` |
| `POST /login` | Проверка `_token`, логина и пароля |
| `POST /logout` | Выход с проверками `auth` и CSRF |

`UserRepository::verifyAdmin()` принимает только существующего пользователя
из `users`, с `deleted_at = null` и `is_admin = 1`. Пароль проверяется через
`password_verify`. Обычному пользователю одних назначенных ролей сейчас
недостаточно для входа: это ограничение текущего `AdminAuthenticator`.

Успех даёт 302 на `/admin`. Неверные данные — 422 с формой. Лимит по IP:
пять попыток в кэше с TTL 60 секунд, последующая попытка — 429. Успешный
редирект на `/admin` сбрасывает счётчик. Реализация использует get/put,
поэтому это не атомарный распределённый rate limiter.

## Сессия и её отзыв

В браузере используется native PHP-сессия `mydomo`, а не старая `prj`.
Cookie: HttpOnly, SameSite=Strict, только cookie, без передачи ID в URL.
Secure определяется текущим `$_SERVER['HTTPS']`; отдельная настройка
доверенных reverse proxy новым сессионным слоем не реализована.

После входа ID сессии обновляется. В ней хранятся `id`, `username`, `name`,
`is_admin`, `stamp`; последний — SHA-256 текущего хеша пароля, не пароль.
На каждом маршруте с `auth` middleware `AuthenticateAdmin` сверяет данные
с `UserRepository::sessionUser(int $id): ?array`.

Сессия прекращается, если пользователь удалён, снят `is_admin`, изменён
пароль или отпечаток отсутствует/не совпадает/не является строкой.
Профиль `/admin/profile` после собственной смены пароля обновляет текущую
сессию; остальные сессии со старым отпечатком перестают проходить проверку.

Гость при обычном GET получает 302 на `/login`. JSON-запрос, запрос с
`HX-Request: true` и изменяющий запрос получают 401 с ошибкой
`authentication_required`. API-клиенту следует явно посылать
`Accept: application/json`.

## CSRF

Для изменяющих браузерных запросов нужен `X-CSRF-Token` или поле `_token`.
При наличии заголовка он имеет приоритет. GET/HEAD/OPTIONS пропускаются
`VerifyCsrfToken`; неверный токен даёт 403 `csrf_failed`.

В Blade токен передаётся из `SessionStore::csrfToken()`. Шаблоны панели
также публикуют meta `csrf-token`, которое использует локальный JS API.
Публичный webhook аутентифицируется собственным секретом и не использует
браузерный CSRF: см. [api.md](api.md).

Yoyo доступен только после входа: POST `/yoyo` защищён CSRF, GET `/yoyo`
предназначен для UI-компонентов. Бизнес-операции нельзя помещать в GET-
обработчики Yoyo, рассчитывая на проверку токена. Оболочка `mydomo.js`
добавляет `X-CSRF-Token` из meta-тега к каждому запросу Yoyo/htmx, поэтому
изменяющие действия компонентов используют `yoyo:post` и проходят CSRF;
пример — категории сценариев `script-categories`.

## Роли и разрешения

Таблицы: `roles`, `permissions`, `role_permissions`, `user_roles`.
`RoleRepository` читает назначения, `Authorization::can($permission)`
проверяет разрешение, middleware задаётся как `can:users.manage`.
`*` разрешает любое действие. `/roles` и управление токенами требуют
`users.manage`, управление обслуживанием — `settings.manage`.

Текущее поведение `Authorization` шире строгой проверки БД:

- непустой список разрешений проверяется по точному имени или `*`;
- при пустом списке либо ошибке чтения используется сессионный `is_admin`;
- `isAdmin()` учитывает роль `admin`, затем флаг сессии;
- вошедший пользователь получает `panel.view` в резервной ветке.

Поэтому удаление назначения роли не равнозначно снятию `is_admin` и не
гарантирует отзыв всех действий. Нельзя документировать этот механизм как
fail-closed. Страницы ядра в основном защищены `auth`; отдельная granular-
проверка каждой CRUD-операции пока не введена. Это факты текущего кода,
а не рекомендуемый способ расширять контроль доступа.

## API-токены

Токен выпускается в `/admin/tokens` или `api:token`, открыто показывается
один раз; в `api_tokens` хранится SHA-256. Заголовок `Authorization: Bearer`
проверяется первым, `X-API-Key` — если Bearer не передан. Передача токена
в query string новым middleware не предусмотрена.

Проверяются `deleted_at`, `revoked_at` и `expires_at` токена, обновляется
`last_used_at`. Текущий поиск не проверяет удаление/статус его владельца:
при отзыве доступа нужно отзывать и токены. Токен не открывает браузерную
панель и панельные `/api/v1/panel/*`, требующие сессии.

Точный перечень защищённых URL и форматы ответов — в [api.md](api.md).
Первичное создание администратора и риски передачи пароля аргументом
описаны в [console.md](console.md).
