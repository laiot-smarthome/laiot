# Zigbee

Zigbee — встроенный модуль ядра `modules/core/zigbee` для Zigbee2MQTT. Он
зависит от MQTT-модуля: собственного клиента и отдельного цикла нет. Модуль
можно выключить на `/admin/modules`, но нельзя установить или удалить; данные
экземпляров, устройств и привязок при выключении сохраняются.

Пользовательская модель та же, что в alpha: экземпляры с корневыми топиками,
раздел «Обнаруженные», привязка свойства к объекту/методу, преобразования,
обратная запись, комнаты и мониторинг. Реализация новая: SDK-модуль,
`ModuleDb`, очередь модуля и Yoyo.

## Транспорт

Модуль регистрирует себя в реестре MQTT-интеграций при boot:

```php
$integrations->addLazy('zigbee', static fn (): MqttIntegration => $container->make(MqttIntegration::class));
```

MQTT-цикл подписывается на настройки модуля плюс фильтры интеграций
(`<base_topic>/#`). Каждое входящее сообщение сначала получает владелец топика.
Zigbee не разбирает его в цикле приёма: `enqueue()` кладёт задание
`zigbee.message` в очередь `module.zigbee`, а разбор идёт в worker-е модуля.
«Ничей» топик по-прежнему обрабатывают привязки MQTT, поэтому дерево топиков не
засоряется чужими пакетами.

Большой retained-пакет `bridge/devices` сжимается (`deflate` + base64) и
восстанавливается обработчиком: задание очереди не должно упираться в предел
`text` MySQL. Смена набора фильтров (новый или выключенный экземпляр) замечена
MQTT-циклом в течение нескольких секунд и вызывает переподключение подписки;
уже запущенный процесс интеграции после выключения модуля доработает до
перезапуска worker-а.

Контракт реестра — `MajorDoMo\Mqtt\Integration`: `id()`, `topics()`,
`owns()`, `enqueue()`. Регистрация ленивая, потому что сервисы модуля зависят
от `ModuleManager`; ранняя сборка дала бы рекурсию через
`NotificationService`.

Доставка — «как минимум один раз»: `QueueWorker` повторяет упавшее задание,
а ошибка после частичной записи может повторить обработчик. Обработчик обязан
допускать повторный вызов.

## Данные

Core-модуль не проходит `module:install`, поэтому семь таблиц создаются при
первом обращении (`Schema`):

| Логическая | Физическая | Что хранит |
| --- | --- | --- |
| `bridges` | `module_zigbee_bridges` | название, корневой топик, включение, состояние, последняя связь |
| `devices` | `module_zigbee_devices` | экземпляр, IEEE, friendly name, модель, статус, комната, метаданные |
| `properties` | `module_zigbee_properties` | путь свойства, exposes, исходное и преобразованное значение |
| `bindings` | `module_zigbee_bindings` | объект/свойство/метод, режим события, правила приёма и отправки |
| `events` | `module_zigbee_events` | диагностический журнал, до 1000 записей на экземпляр |
| `health_settings` | `module_zigbee_health_settings` | глобальные настройки мониторинга |
| `health_state` | `module_zigbee_health_state` | сохранённые инциденты и квитанции каналов |

Внешние ключи не используются: связь между таблицами и каскад удаления делает
`Repository`. JOIN и raw SQL в модуле недоступны — это граница `ModuleDb`.
Транзакция своих изменений открывается через `ModuleDb::transaction()`.

Значения хранятся как JSON, поэтому `null`, `false`, `0`, `"0"` и `""`
различаются. `raw_value` — исходное сообщение, `value` — результат правила
приёма, `last_delivered` — последнее успешно доставленное значение привязки.
Повторное сообщение не считается успешной доставкой.

## Обнаружение и добавление

- `bridge/devices` создаёт или обновляет устройства и свойства из `exposes`.
- Первое сообщение устройства тоже создаёт запись: сначала приходит
  `friendly_name`, затем полное описание с IEEE-адресом. Ранняя запись без IEEE
  объединяется с полной, привязки и комната переходят на итоговую строку.
- Статус `discovered` означает «только сбор данных»: обработчики, команды и
  комната не выполняются. `added` включает обработку.
- Входящее MQTT-сообщение не подтверждает добавление: это выбор пользователя.
- Переименование в Zigbee2MQTT сохраняет привязки, потому что устройство
  определяется экземпляром и IEEE-адресом.
- `bridge/state`, `bridge/info`, `bridge/event`, `bridge/response/*` и
  `bridge/logging` обновляют состояние и журнал. Запросы `bridge/request/*` и
  определения конвертеров игнорируются.

Корень существующего экземпляра менять нельзя, корни разных экземпляров не
должны пересекаться: иначе топик попадёт в два обработчика.

## Привязки и преобразования

Приём и отправка настраиваются независимо:

| Режим | Смысл |
| --- | --- |
| `none` | без изменений |
| `binary` | `ON/OFF`, `true/false` ↔ `1/0` |
| `exposes` | `value_on`/`value_off` конкретного устройства |
| `map` | своя таблица замен с учётом или без учёта регистра |
| `number` | множитель, смещение, округление 0–8 знаков |
| `invert` | `1` ↔ `0` |

Правило проверяется при сохранении; код не выполняется. В таблице замен
`1` — число, `true` — логическое, `"1"` — строка, `null` — JSON null.
«Проверить» на странице свойства применяет правило и показывает результат,
ничего не сохраняя.

Порядок доставки: исходное сообщение → приём → запись свойства объекта →
OnChange ядра → дополнительный метод → уведомление комнаты. Ошибка одного
свойства не останавливает остальные, но после обработки всех поднимается в
очередь для повтора.

Режим `change` сравнивает преобразованное значение с `last_delivered`; ошибка
не помечает значение доставленным. `action:<вид>` — отдельное свойство с
временем приёма до микросекунд, поэтому повторное нажатие меняет значение и
снова запускает OnChange. Обычное `action` остаётся отдельным свойством.

Запись в объект идёт через `PropertyValueService` с источником
`zigbee:<base>/<friendly_name>:<path>`; собственное эхо модуль не отправляет
обратно. Дополнительный метод получает `VALUE`, `NEW_VALUE`, `OLD_VALUE`,
`RAW_VALUE`, `TITLE`, `SOURCE`, `IEEE_ADDRESS`, `BRIDGE_ID`; в OnChange
действует обычный контракт ядра.

## Комнаты

Комната устройства выбирается в карточке. Если у комнаты есть объект,
уведомляется метод `deviceChanged` для **каждого свойства каждого сообщения**,
включая повторы и привязки с фильтром «только изменение». Параметры:
`DEVICE_ID`, `DEVICE_NAME`, `DEVICE_TITLE`, `IEEE_ADDRESS`, `BRIDGE_ID`,
`BASE_TOPIC`, `LOCATION_ID`, `TOPIC`, `PROPERTY`/`TITLE`, `VALUE`,
`NEW_VALUE`, `OLD_VALUE`, `RAW_VALUE`, `SOURCE`.

Метод `Rooms.deviceChanged` создаётся один раз при первом уведомлении, если
класс `Rooms` уже существует; существующий код не перезаписывается. Создание
идёт через `MethodRepository`, то есть через публичный сервис ядра, а не
записью в таблицу методов.

## Управление

Разрешение записи, диапазоны и варианты значений берутся из `exposes`.
Обратная запись включается галочкой у привязки: модуль подписывается на
свойство объекта через `$context->subscriptions()` и снимает подписку, когда
привязка меняется или удаляется. Исходящее правило применяется до проверки
`exposes`; команда уходит в `<base_topic>/<friendly_name>/set` вложенным JSON,
например `{"color":{"x":0.5}}`.

Ручная команда на странице свойства проверяет те же ограничения. Успешная
постановка в очередь MQTT не подменяет подтверждение устройства: фактическое
значение обновится его сообщением.

На странице экземпляров доступны реальные команды Zigbee2MQTT через
`bridge/request/<command>`: `permit_join`, `device/rename`, `device/remove`,
`device/configure`, `device/interview`, `device/options`, `health_check`,
`networkmap`. Параметры — JSON-объект; `transaction` добавляется автоматически.

## Мониторинг

Задача `monitor` в worker-е модуля раз в минуту проверяет MQTT-транспорт,
экземпляры и добавленные устройства. Инциденты (`offline`, `online`,
`battery_low`, `battery_critical`, `battery_ok`) хранятся в `health_state`,
поэтому повторный проход не дублирует уведомления. Настройки глобальные, у
устройства может быть своё переопределение или наследование.

Заряд берётся из `battery`, из `battery_low` или оценивается по напряжению
(профиль `linear3v`, `alkaline`, своя таблица). Оценка приблизительная: заведомо
чужой масштаб напряжения не превращается в 100%. Ошибки обработчиков пишутся
в журнал модуля. При недоступном MQTT-цикле или брокере события устройств
подавляются, чтобы не рассылать лавину.

Канал `notify` создаёт уведомление панели (`NotificationService`, модуль
`zigbee`), канал `code` выполняет доверенный PHP без открывающих тегов и
получает `$params`. Это не sandbox; синтаксис проверяется до сохранения.

## Workers и CLI

```bash
php bin/mydomo worker zigbee          # мониторинг + очередь module.zigbee
php bin/mydomo core-worker module.zigbee   # только доставка сообщений
```

`worker zigbee` обслуживает и задачи модуля, и очередь `module.zigbee`;
`core-worker module.zigbee` — только очередь. Одновременно оба процесса не
конфликтуют: очередь защищена блокировкой. Без worker-а сообщения копятся в
`module.zigbee`, а мониторинг не выполняется.

## Интерфейс

| Страница | Что делает |
| --- | --- |
| `/module/zigbee` | найденные и добавленные устройства, Yoyo-список, поиск, комнаты, массовое добавление |
| `/module/zigbee/devices/<id>` | название, комната, свойства, переопределение мониторинга |
| `/module/zigbee/properties/<id>` | привязка, правила приёма/отправки, проверка, ручная команда, `exposes` |
| `/module/zigbee/bridges` | экземпляры, корневые топики, команды Zigbee2MQTT |
| `/module/zigbee/monitoring` | глобальные пороги и события |
| `/module/zigbee/journal` | журнал с фильтрами (Yoyo) |

Изменяющие действия — обычные POST с CSRF и Notify; список и журнал
перерисовываются через `/yoyo`. Доступ требует `settings.manage`, как у MQTT.

## Ограничения

- импорт данных alpha `zigbee`/`zigbeedev` не входит в модуль и остаётся
  отдельной операцией; старые таблицы не читаются;
- собственного MQTT-клиента нет, Zigbee работает только вместе с включённым
  MQTT-модулем;
- при выключении модуля уже запущенный MQTT-цикл держит его подписки до
  перезапуска worker-а;
- картинки устройств с сайта Zigbee2MQTT не загружаются: панель не делает
  внешних запросов;
- журнал ограничен 1000 записей на экземпляр и не является архивом;
- переопределения мониторинга — общая схема; отдельных порогов на каждое
  событие батареи у устройства нет;
- `networkmap` возвращает данные в `bridge/response/networkmap`, которые
  сейчас попадают только в журнал, без визуализации карты.

Проверки: `tests/Feature/ZigbeeModuleTest.php` — lifecycle, страницы,
обнаружение, доставка в объект и комнату, преобразования, обратная отправка,
очередь, мониторинг и Yoyo (SQLite, без брокера); `module:check zigbee`
проверяет отсутствие legacy-вызовов.
